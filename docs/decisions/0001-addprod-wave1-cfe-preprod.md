# ADR-0001: CFE для пилота волны 1 AddProd без релиза conf-main

- **Статус:** accepted (уточнение 2026-10-21: поэтапное подключение)
- **Дата:** 2026-10-21
- **Участники:** PM TB, wave 1 APNS-010…012
- **Репозитории:** `extensions` (артефакт), `conf-main` (источник diff / эталон после merge)

## Контекст

Волна 1 ещё не влита в prod-конфигурацию. Нужен пилот на проде/прод-подобной ИБ **до** финального релиза `conf-main`. Проверку разбиваем: сначала только HTTP `offerings/list`, затем отдельно `parity/observations` (и `not_called`).

Волна 0 (клиент, настройки, карта, журнал/API observations) уже в main и может быть на контуре.

## Решение

Два расширения (не одно «всё сразу»):

| Этап | CFE | Jira / APNS | Что делает | Что не делает |
|------|-----|-------------|------------|---------------|
| **1** | `DEV_78570` | DEV-78570 / APNS-010 | Shadow-вызов `offerings/list` в точках `available` / `shown`; fail-open; privileged на новые метаданные настроек/клиента | **Не** шлёт `parity/observations`; не `not_called`-gate |
| **2** | `DEV_78571` (или `DEV_78571`+тонкий `DEV_78572`) | DEV-78571 / APNS-011 (+012) | После list (или вместо «тихого» list-only) — сборка и POST observations; `not_called` вне карты | Не подменяет результат 1С |

Порядок на проде: сначала подключить **только** `DEV_78570` + режим **Shadow** → убедиться в list/журнале HTTP без observations → затем `DEV_78571` (+012 при необходимости).

Общие правила:

1. `ConfigurationExtensionPurpose = Patch` (или Customization по стилю TB_ext), заимствование объектов, `&После` / `&ИзменениеИКонтроль`.
2. Источник поведения — tip worktree/MR соответствующих DEV-*; относительно **prod/main без волны 1**.
3. Предусловие ИБ: волна 0 на месте. Режим настроек = **Shadow**.
4. После merge волны 1 в conf-main — снять оба CFE (паттерн авто-отключения TB_ext), чтобы не двоить логику. Баги пилота закрываем **в тех же** MR волны 1 (!6351/!6348/!6349) до влития — реестр [cfe-pilot-findings-for-conf-main.md](../analysis/AddProdNewService/cfe-pilot-findings-for-conf-main.md); отдельные post-merge follow-up не заводим.
5. Этап 2 **зависит** от этапа 1 (или вбирает list, если 78570 уже снят и list уезжает в main) — явно не включать observations в `DEV_78570`.

## Последствия

- Плюс: можно отладить list/маппинг/fail-open на бою, не засоряя сервис observations и не смешивая дефекты.
- Плюс: откат этапа 2 = снять второе CFE, list-пилот может остаться.
- Риск: два артефакта и порядок подключения; drift vs MR tip.
- Не включает dual-write / select / confirm / service-primary.

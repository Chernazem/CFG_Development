# Обработка очереди платежей

## Точка входа

Регламентное задание вызывает `ОбработкаПлатежейСлужебный.ОбработкаОчередиПлатежей`.

Стек запуска:

1. `ОбработкаОчередиПлатежей`
2. `ОбщегоНазначения.ПриНачалеВыполненияРегламентногоЗадания`
3. проверка `ИспользоватьОбработкуПлатежей`
4. `ОбработкаПлатежейПовтИсп.НастройкиПодсистемы`
5. `МаксимальноеКоличествоПотоковОбработкиОчередиПлатежей`
6. `ИмяМетодаОбработкаОчередиПлатежейВыполнитьВФоне`
7. запуск фоновых заданий `ОбработатьОчередьПлатежей`

Стек RMQ-обработки:

1. `ОбработатьОчередь`
2. `ПараметрыПодключения` по виду `ОбработкаПлатежей`
3. `ОчередьСообщений.НовыйПодписчик`
4. `ОбработатьСообщение`
5. `РезультатОбработкиСообщения`
6. `ОбработкаПлатежей.ОбработкаВходящегоПлатежа`
7. `ОтправитьОтвет`

Стек Kafka-обработки:

1. `ОбработатьОчередьKafka`
2. `ИнициализироватьПолучателяОбработкиПлатежейКафка`
3. `ПрочитатьСообщениеПлатежаКафкаСОбработкойИсключений`
4. `ОбработатьСообщениеKafka`
5. `ОбработкаПлатежей.ОбработкаВходящегоПлатежаKafka`
6. `ЗафиксироватьСмещениеОбработанногоСообщенияПлатежаКафка`
7. при исключении `ОтправитьСообщениеKafkaСОшибкойВОтдельнуюОчередь`

## Читаемые объекты базы

- Константа `ИспользоватьОбработкуПлатежей` — общий выключатель регламента.
- Константа `НастройкиОбработкиПлатежей` и `Справочник.НастройкиОбработкиПлатежей` — количество потоков, флаг уведомлений, уровень логирования, брокер сообщений.
- `СтандартныеПодключения`:
  - `ОбработкаПлатежей` для RMQ;
  - `ОбработкаПлатежейKafka` для Kafka;
  - `ОчередьСообщенийKafkaСОшибкамиВОбработкеПлатежей` для отправки ошибочных Kafka-сообщений.
- `Справочник.ПлатежныеСистемы` — поиск платежной системы по внешнему идентификатору.
- Существующие документы оплаты проверяются через `ТБ_ОбменСЛичнымКабинетом.ПлатежУжеЕстьВСистеме`.

## Изменяемые и создаваемые объекты базы

Основное создание выполняет `ОбработкаПлатежей`:

- `Документ.ОплатаЧерезПлатежнуюСистему` или связанные платежные документы по договору контрагента;
- документы оплаты по заявке на выдачу займа, включая сценарии продления;
- документы оплаты дополнительных продуктов через `УправлениеДополнительнымиПродуктами`;
- данные рекуррентного платежа и маски карты через обработчики личного кабинета;
- очередь уведомлений ответственным лицам об оплате, если это включено настройкой.

Для защиты от дублей внутри транзакции ставится исключительная блокировка данных по `Документ.ОплатаЧерезПлатежнуюСистему.ИдентификаторПлатежа`.

## Что, куда и когда

При каждом запуске регламент доводит количество активных фоновых заданий `ОбработатьОчередьПлатежей` до расчетного максимума. Уже работающие обработчики не дублируются.

RMQ-обработчик читает сообщение, сохраняет `ReplyTo` и `CorrelationId`, обрабатывает платеж и подтверждает сообщение. Даже при исключении сообщение подтверждается, но отправителю возвращается ответ с HTTP-кодом 500 и структурой ошибки.

Kafka-обработчик отключает автоматическую фиксацию смещения. Смещение фиксируется только после успешной обработки платежа. Если десериализация или валидация показала некорректное сообщение без исключения, обработка пропускается по правилам модуля. Если возникло исключение, исходное сообщение с описанием ошибки публикуется в отдельную тему ошибок, после чего смещение фиксируется для предотвращения бесконечного повторения.

Сам платеж обрабатывается в транзакции: проверяются параметры, формируется структура заполнения, блокируется идентификатор платежа, проверяется уникальность и создается документ оплаты. После фиксации транзакции отправляются уведомления ответственным, чтобы уведомления не уходили по платежу, который не был записан.

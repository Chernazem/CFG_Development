## Просьба 1. `available` и `shown`

**Да, закладываем оба среза до релиза волны 1.**

- `available` — снимок в `ПрограммныйИнтерфейсДополнительныеПродукты.ПодобратьДополнительныеПродукты`.
- `shown` — после ручного отбора на `ЗаявкаНаВыдачуЗайма.ПодборДополнительныхПродуктов`.
- Где ручного отбора нет (remote/tb_api) — `shown` = копия `available`.
- Ключи обязательны всегда; пустой массив допустим, опущенный ключ — нет.
- `decision_id`: при `outcome: "ok"` — UUID из ответа `offerings/list` (одна строка, не массив); иначе явный `null` (ключ присутствует). Уточнение круга 6: [answers-round-6.md](answers-round-6.md).

## Просьба 2. APNS-063 после APNS-060

**Да, разводим по времени.** APNS-060 переключает подбор; легаси-матчинг после него — теневая сторона. APNS-063 не в том же заходе. Длительность наблюдения — из порога готовности по вашим данным, не заранее.

После cutover: `shown_to_client: "service"`, в `shown` — то, что осталось на форме (ваши коды), в `available` — легаси, пока жив.

## Просьба 3. ПДн

**Да.** В наблюдении только коды настроек, названия, цены, сроки, `client_ref` / `external_ref`. ФИО, телефон, паспорт, номера договоров не кладём. Нарушение считаем дефектом интеграции.

## APNS-012

Непокрытая номенклатура не скрывается: наблюдение с `service_call.outcome: "not_called"` (и `decision_id: null`) всё равно уходит.

# Соответствие блоков и пробелы

## Карта трех заявленных блоков

| Блок | 1С сейчас | Сервис | Dual-run |
| --- | --- | --- | --- |
| Подбор по заявке | `ПодобратьДополнительныеПродукты` / форма `ПодборДополнительныхПродуктов` / `GetClientAvailableAdditionalProducts` | `POST /api/v1/offerings/list` | Вызвать оба, сравнить состав и цены, клиенту показывать 1С. Расхождения писать в лог/журнал сравнения |
| Фиксация выбора | `ДополнительныеРеквизитыДополнительногоПродукта` / `EditLoanRequestAdditionalProducts` | `POST /api/v1/offerings/select` по `decision_id` + `offer_ids` | Писать в 1С как сейчас; select поздно (TTL 30 мин), `external_ref` = GUID заявки |
| Активация / оплата | `СформироватьДокументыДополнительныхПродуктов` + отдельное ППИ после включения в тело / ПС / `Заключен` или `ОжидаетОплаты` | `sales/confirm` затем `sales/payment` | Confirm в точке оформления (подпись, выдача). Payment в точке ППИ (или ПС). Не слать payment «вместо» включения в тело |

`sales/list` на dual-run нужен как read-model для сверки, не как замена `GetLoanRequestAdditionalProducts`.

Развернутые ответы: [blockers-answers.md](blockers-answers.md), [answers-from-service.md](answers-from-service.md).

## Пропущенные блоки (дополнить исходный план)

Эти контуры либо есть в ТБ и влияют на выдачу, либо уже есть в API сервиса и без них dual-run сломается.

1. **Карта идентификаторов НСИ.** Сервис говорит `product_code` / `tariff_code` / UUID. ТБ говорит ссылки `Справочники.ДополнительныеПродукты`, `Справочники.ПрограммыСтрахования`, `Справочники.НастройкиДополнительныхПродуктов`. Без явной карты dual-run нельзя даже сравнить.
2. **Кто master каталога на dual-run.** После переключения владелец - сервис. На dual-run не два редактора: публикация в сервисе, в ТБ карта/проекция. Writer ERP ТБ выключается только вместе с реле сервиса.
3. **Обязательные продукты.** `РС ОбязательныеДополнительныеПродукты` — вид займа + канал + продукт. Флага в каталоге нет и на dual-run не будет (В-4).
4. **Черный список жалоб.** Ключ РС — `Контрагент`. API заливки нет (S-24); до заливки фильтр сервиса пустой, проверка ТБ обязана остаться.
5. **Влияние на тело, график, лимиты КЛ.** Стоимость допов участвует в сумме оформления и лимите. Сервис считает `total_price`, но не двигает график ТБ. Даже после cutover расчет графика останется в 1С; нужно строгое равенство цены.
6. **Способ включения в тело.** `ВключатьВТелоЗайма` <-> `payment_mode = financed` (сумма займа растет, затем ППИ). `ИсключатьИзТелаЗайма` <-> `upfront` (разовый платеж клиента). Назначение ППИ - `payment_purpose` снимка оффера.
7. **Печать и комплект документов.** 1С: `ПечатьДопПродуктов`, заявления. Сервис: `contract_draft.print_payload`, admin `erp/documents/render`. Dual-run: печатаем 1С, payload сервиса складываем рядом для сверки.
8. **Лицензионные ключи и расход услуги.** 1С: `GetAdditionalProductLicenseKey`. Сервис: `sales/consume` + entitlements. Это четвертый блок жизненного цикла после оплаты.
9. **Отмена и возврат.** Draft: `offerings/release`. После confirm: `sales/cancel` + `refund_channel`. `expired` = TTL, не отказ.
10. **Продление.** Отдельный контур ТБ (`ИспользоватьПродажуДополнительныхПродуктовПриПродлении`, РС к оплате). В сервисе есть `deal_scenario=prolongation`.
11. **Рефинансирование транша КЛ.** `GetReissueTrancheAvailableAdditionalProducts`; в сервисе `coverage_scope.kind=credit_line_tranche` и `deal_scenario=refinancing`.
12. **Реестры партнерам.** СберЗдоровье / PharmIQ / Euroins уже в `registry_data` confirm и в `registries/*`. В ТБ это отдельные документы и ключи, не общий HTTP.
13. **Агентская схема, мотивация, отчеты.** Остаются в 1С на всю программу dual-run. В вынос пилота не входят, пока явно не попросим.
14. **Технический клиент и идемпотентность.** 403 admin-cookie ожидаем. ТБ нужен JWT источника. Ключи: `external_ref`, `payment_ref`, `cancel_ref`, `usage_ref`.
15. **Узкий пилот каталога.** Живые: `cashback`, `guarantee`, `sberhealth`, `unemployment` + комбо `guarantee_health_start`. Карта: `legacy_setting_id` настроек. Весь зоопарк `ДоговорДополнительногоПродукта*` сразу не сравнить.

## Что сознательно не выносим в первой программе

- проведение договоров займа и ИУ;
- касса, РКО, график платежей займа;
- агентские договоры и комиссии;
- мотивация сотрудников;
- полный зоопарк печатных форм, пока payload сервиса не совпал с 1С.

## Риски dual-run

- Два независимых расчета цены разъедутся из-за СКД, округления, кратности периода, подразделения.
- `expires_at` = 30 мин от list, select не продлевает; на офисной заявке select только у формирования документов.
- Повторный select по той же заявке штатный до confirm; `activation_id` при замене состава меняются.
- `sales/cancel` не снимает draft (409); до S-21 бронь истекает в `expired`.
- Окно между `sales/confirm` и созданием ППИ: в сервисе `money_state = pending`, в ТБ заем уже выдан. Это штатная двухфазность (9,1% продаж ждут оплату), не баг. `payment_ref` = факт ППИ (или ПС), не ИУ.
- Confirm без последующего payment оставит сервис в `pending` навсегда только если ППИ/ПС так и не ушло - тогда это расхождение, которое надо ловить журналом, а не «считать включение в тело оплатой».

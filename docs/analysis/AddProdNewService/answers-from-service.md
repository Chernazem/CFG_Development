## 0. Четыре факта, с которых стоит начать

**0.1. TTL оффера — 30 минут, и `select` его НЕ продлевает.**
`OFFER_TTL = timedelta(minutes=30)` (`backend/api/src/api/v1/offerings.py:44`).
`selection.expires_at = min(now + TTL, expires_at всех выбранных офферов)`
(`selection.py:309`) — комментарий там прямо говорит: бронь не продлевает договорный оффер.
`sales/confirm` позже `expires_at` → 409 `SELECTION_EXPIRED` (`selection.py:530`).

Следствие для APNS-020/APNS-022: в офисном сценарии, где между подбором и выдачей часы,
`offerings/list` + `offerings/select` надо звать **поздно** — на шаге, непосредственно
предшествующем формированию документов, а не в момент подбора на форме. Ранний select
гарантированно протухнет. Повторить `list`+`select` по тому же `external_ref` можно
(см. S-14) — это штатный путь, а не обход.

При этом сами 30 минут мы считаем нашей слабой стороной: этим числом склеены два разных
срока — актуальность цены (истекает со сменой версии тарифа, то есть месяцы) и жизнь брони
(истекает, когда сделка не состоялась). Пересматриваем, см. В-3 — нужен ваш реальный разброс
времени между подбором и выдачей.

**0.2. `sales/cancel` не отменяет неподтверждённую бронь.**
`cancel_activation` пропускает только позиции в состоянии `active`/`completed` либо
`contract_state = 'signed'`; всё остальное → 409 `ACTIVATION_NOT_CANCELLABLE`
(`cancellation.py:184-193`). После одного лишь `offerings/select` позиция —
`contract_state = 'draft'`, то есть **не отменяемая**. APNS-021 в нынешней формулировке
(«бронь есть, оформление не состоялось → `sales/cancel`, `draft → cancelled`») сегодня даст
409. Сейчас такая бронь просто истекает по TTL (черновик договора переводит в `expired`
крон `expire_additional_product_drafts`, раз в 60 с, `entrypoints/cron.py:99`).

Пробел наш: явного события «бронь снята» нет вообще, а оно нужно — молчание неотличимо от
сбоя. Делаем отдельную операцию снятия брони (`offerings/release`, задача S-21): причина
обязательна, деньги и ЕРП не затрагиваются. Обязательной для вас не будет — не позвали,
бронь истечёт сама, но тогда в аналитике это `expired`, а не отказ клиента.

**0.3. `payment_ref` — один на одну активацию, `amount` обязан посимвольно совпасть с ценой
позиции.**
`payment_ref`, уже использованный для другой активации → 409 `PAYMENT_IDEMPOTENCY_CONFLICT`
(`payment.py:242-245`); сумма ≠ `activation.price` → 409 `PAYMENT_AMOUNT_MISMATCH`
(`payment.py:302-305`). Если ТБ формирует **одно** `ПлатежноеПоручениеИсходящее` на несколько
доп-продуктов одной заявки — текущий контракт это не примет ни по ключу, ни по сумме.
Вопрос обратно в ТБ — В-1 в конце документа.

**0.4. Токен — `POST /api/v1/auth/token`, дальше `Authorization: Bearer`.**
Cookie, CSRF-заголовки и refresh для вашего канала не нужны: серверный клиент получает JWT в
теле ответа и носит его в заголовке. Подробности и примеры — в `dev-access.md`.

## Доступ

### S-01. JWT источника витрины для ТБ

**Код источника — `centrofinance`.** Он зашит как канонический код ТБ в бэкфилле миграции
`0018_ap_source_scoped_identity` (`SEED_SOURCE_CODE = "centrofinance"`,
`backend/database/migrations/versions/20260805_0018_ap_source_scoped_identity.py:56`). Для
dual-run заводим ровно его, с `requires_loan_context = true`, `confirm_policy = 'explicit'`.
`e2e_tb_sim` — **не** ваш источник: это наш симулятор канала 1, у него есть право на тестовый
контур, которого у ТБ не будет.

`source_id` в теле запроса не передаётся никогда. Источник берётся из учётки
(`principal.source_id`, `offerings.py:87`), и `external_ref` уникален только внутри источника.

**Точные scope.** Роль `integration` (`constants/permissions.py:97-108`) даёт ровно:

```
additional_products.offerings.read
additional_products.offerings.select
additional_products.sales.confirm
additional_products.sales.read
additional_products.sales.consume
additional_products.sales.usage_correct
additional_products.sales.payment
additional_products.sales.cancel
```

Ваш список совпадает; сверх него роль несёт `sales.consume` и `sales.usage_correct` (списание
и коррекция оказанной услуги — понадобятся на волне 5, APNS-052). Права
`additional_products.offerings.test` у роли **нет** намеренно: с `contour = "test"` витрина
показывает неопубликованные версии, реальному клиенту они уехать не должны. Все запросы ТБ
идут с `contour = "production"` (значение по умолчанию, поле можно не слать).

Права в JWT не кладутся — они выводятся из роли на каждом запросе (`auth_provider.py:154-156`),
поэтому изменение роли действует немедленно, без переиздания токена.

**Как получить токен.**

```
POST /api/v1/auth/token
Content-Type: application/json

{"email": "<учётка источника>", "password": "<пароль>"}

→ {"access_token": "<jwt>", "token_type": "Bearer", "expires_in": 3600}
```

Дальше на каждый вызов — `Authorization: Bearer <jwt>`. Токен живёт час, по 401 берётся
новый тем же запросом. Пример минимального запроса витрины:

```
POST /api/v1/offerings/list
Authorization: Bearer <jwt>
Content-Type: application/json

{
  "client_ref": "8b0c1e14-...-контрагент-1С",
  "requested_amount": "50000.00",
  "term_days": 30,
  "operation_kind": "issue",
  "loan_kind": "standard",
  "channel": "office"
}
```

`requested_amount`/`term_days`/`operation_kind`/`loan_kind` для `centrofinance` обязательны:
`requires_loan_context = true` → без них 422 `LOAN_CONTEXT_REQUIRED`
(`catalog.py:455-472`).

Логин/пароль учётки — в вашем хранилище секретов (константа или защищённый реквизит, не в
коде обработки). Отзыв доступа мгновенный на нашей стороне и не ждёт истечения токена.

Учётка и примеры для дев-стенда — отдельным файлом `dev-access.md`.

**Статус:** учётка заведена, стенд обновлён, полный цикл прогнан 2026-08-25 — реквизиты и
проверенные примеры в `dev-access.md`.

## Контракт запросов

### S-07. Что слать в `external_ref` и `client_ref`

Оба поля — **чужие непрозрачные ключи**, сервис их не парсит и не валидирует как UUID:
`str`, 1–128 символов (`offerings_requests.py:42`, `:144`). Формат выбираете вы, но выбор
фиксируется навсегда, потому что это ключи связи.

Наша рекомендация — **GUID, не номер**:

- `external_ref` = GUID `Документ.ЗаявкаНаВыдачуЗайма`. Это ключ продажи: пара
  (`source_id`, `external_ref`) уникальна, одна заявка = один selection, `sales/list` ищет
  только по нему. Номер (`5СР171559`) годится технически, но он человекочитаемый и живёт
  по своим правилам перенумерации; GUID неизменен.
- `client_ref` = GUID контрагента 1С. Он же — ключ чёрного списка (S-17) и он же обязан
  совпасть с `parties.customer.client_ref` на `confirm` (иначе 409
  `CONTRACT_DRAFT_SNAPSHOT_MISMATCH`, `contract_drafts.py:225-231`). Один и тот же GUID во
  всех трёх местах — иначе фильтр чёрного списка и снимок ЕРП разъедутся молча.

Код ЛК в `client_ref` не годится: он не совпадёт с ключом жалоб в РС.

### S-08. `coverage_scope.scope_id`

`scope_id` — не справочная величина, а **граница однократности**: на паре
(`product_id`, `coverage_scope_kind`, `coverage_scope_id`) стоит частичный уникальный индекс
по подписанным договорам (`uq_ap_activation_signed_scope_once`, миграция
`20260815_0034`). Второй подписанный договор того же продукта в той же границе не пройдёт.

Индекс **глобальный, без `source_id`**, и это осознанно: однократность продукта в границе
займа — свойство займа, а не того, кто его продал; два источника, пишущие в один заём,
обязаны ловить дубль. Отсюда следует требование, которое мы в контракте не записали:
**`scope_id` обязан быть уникален глобально**, а не внутри вашей нумерации.

Поэтому: **GUID договора займа** (`kind = "loan_agreement"`), для транша КЛ — GUID транша
(`kind = "credit_line_tranche"`). Номер (`ЦЗ5СР138420`) подойдёт только с префиксом источника
(`centrofinance:ЦЗ5СР138420`) — понимаем, что номер вам нужен для людей и печатных форм, но
голым в этом поле он небезопасен. Формулировку в контракте поправим, сейчас там просто
«строка до 128 символов» — наш недочёт.

Важно: на момент `select` договора займа может ещё не быть. Тогда либо `select` зовётся
после присвоения номера/GUID договора, либо `scope_id` = GUID заявки при
`kind = "loan_agreement"` — но тогда это должно быть решено один раз и одинаково во всех
точках, иначе однократность перестанет ловить дубли. Ждём вашего решения — В-2.

`ends_at` обязателен, с таймзоной, строго в будущем (`offerings_requests.py:131-140`,
`selection.py:190`).

### S-09. Канон `parties` на `sales/confirm`

**Реализована схема OpenAPI** (`parties.customer` / `parties.seller` / `parties.client_erp`),
плоского `party` из PDF в коде нет. Форму мы защищаем не сильно: в сделке две стороны плюс
довесок для ЕРП, и плоская структура вынуждает префиксовать каждое поле дважды — но если
имена вида `counterparty_erp_guid` вам принципиально удобнее, это обсуждаемо, спор здесь
не содержательный. Плоский `party` из PDF раскладывается во вложенный так:

| PDF | Куда в API |
|---|---|
| `counterparty_erp_guid` | `parties.customer.guid` |
| ИНН клиента | `parties.customer.inn` |
| пол, ДР | `parties.customer.gender`, `parties.customer.birth_date` |
| `partner_erp_guid` | `parties.client_erp.partner_erp_guid` (хранится, в XML пока не рендерится) |
| продающее юрлицо | весь блок `parties.seller` |

**Минимальный обязательный набор** (`contract_drafts.py:102-133`):

`parties.customer`: `client_ref`, `guid`, `full_name`, `inn`, `legal_or_physical`;
при `legal_or_physical = "ФизическоеЛицо"` дополнительно `birth_date`, `gender`.

`parties.seller`: `guid`, `full_name`, `inn`, `kpp`, `bank_account`, `bank_bik`,
`bank_correspondent_account`, `bank_name`, `bank_guid`, `bank_account_guid`,
`subdivision_guid`, `subdivision_name`.

**Ответ на «4xx или дырявый снимок»: строго 4xx.** Нет обязательного поля → 422
`ERP_SNAPSHOT_INCOMPLETE` с перечнем недостающих ключей в `details.missing`, продажа не
подтверждается вообще. Это сознательно: неполный снимок ЕРП — это документ, который потом
никто не сможет ни отправить, ни исправить, и обнаружится он в бухгалтерии через месяц.
Лучше отказ в момент оформления.

Подчеркнём: **список обязательных полей — не наше требование, а требование обмена с ЕРП**
(`erp_xml.py:109-134` собран по вашим же образцам из `ai_docs/xml/`). Если ТБ в момент
продажи не располагает ИНН, полом или ДР, ослаблять проверку бессмысленно — документ всё
равно нечем заполнить. Это ваш S-06: сначала инвентаризация 1С, потом решаем, откуда брать
недостающее.

`parties.client_erp` — свободный словарь без валидации: сюда кладите атрибуты, нужные ЕРП, но
не участвующие в наших проверках (`partner_erp_guid` и т.п.). Он сохраняется в снимке
контекста продажи (`ApSaleContext.client_erp_snapshot`) и попадает в payload ЕРП-команды
(`erp.py:123`); в текущем XML не используется, добавление поля в XML не потребует изменения
контракта запроса.

Считаем это **временным** решением и говорим об этом прямо: поле без схемы не проверяется
никак, и через год мы получим ровно тот дырявый снимок, от которого защищаемся строгой
валидацией выше. Когда список ЕРП-атрибутов у вас стабилизируется — заводим им явные поля.

Ориентир по фактическим значениям — `backend/api/tests/e2e/test_ap_sale_cycle.py:88-124`:
там реальные реквизиты ЦФГ и полный набор полей клиента. Эмпирика оттуда же:
«Организация» на всех четырёх живых видах документов доп-продуктов принимает только два
значения (ЦФГ или ВелкомДеньги) — GUID партнёра (euroins/innmed/pharmiq) в `parties.seller`
не появляется никогда, это другая роль.

### S-10. Канон `loan_context`

Канон — `scope_kind`, `scope_id`, `attributes` (`sales.py:79-82`). Блок **необязателен**, но
если он передан, `scope_kind` и `scope_id` обязаны совпасть с `coverage_scope` из `select` —
иначе 409 `CONTRACT_DRAFT_SNAPSHOT_MISMATCH` (`contract_drafts.py:232-241`).

Поля из PDF (`request_number`, `agreement_number`, сумма, срок) кладутся в `attributes` —
это свободный словарь. Сегодня из него реально потребляются два ключа, и оба идут в
комментарий договора в ЕРП (`erp_xml.py:207-214`):

```json
"loan_context": {
  "scope_kind": "loan_agreement",
  "scope_id": "<GUID договора займа>",
  "attributes": {
    "loan_application_number": "5СР171559",
    "loan_application_date": "2026-08-24"
  }
}
```

Для источника с займом просим слать эти два ключа всегда — без них комментарий
«#Сформировано из заявки на выдачу займа №…» в ЕРП-документе не появится, а он есть в ваших
образцах. Остальные атрибуты (сумма, срок, вид займа) слать можно и полезно для разбора
расхождений, но обязательными они не являются.

**Не реализован.** В `SalesConfirmRequest` (`sales.py:85-95`) полей оплаты нет и в OpenAPI

## Поведение витрины

### S-13. Сроки жизни и что делать на длинной офисной заявке

| Сущность | Срок | Что при истечении |
|---|---|---|
| `decision` / `offer` | 30 мин от `offerings/list` | `select` по такому офферу → 409 `OFFER_UNAVAILABLE` (`selection.py:224`) |
| `selection` | `min(select + 30 мин, срок оффера)` | `confirm` → 409 `SELECTION_EXPIRED` |
| `contract_draft` | равен `selection.expires_at` | крон переводит в `expired` (раз в 60 с); подписание → 409 `CONTRACT_DRAFT_EXPIRED` |

Отдельного «протухания» строки selection нет — она остаётся `reserved` с прошедшим
`expires_at`, и её можно перезаписать новым `select` (S-14).

**Повторить `list` + `select` по тому же `external_ref` можно — это штатный путь**, и
именно так надо жить на длинной офисной заявке. Ограничение одно: после успешного
`sales/confirm` (`selection.state = 'active'`) повторный `select` даст 409 «Подтверждённый
выбор по заявке нельзя заменить» (`selection.py:273`).

Практическое правило для APNS-020: **`select` зовём максимально близко к формированию
документов**, а не на шаге подбора. Если между `select` и `confirm` прошло больше 30 минут —
`list`+`select` заново и только потом `confirm`.

Это правило — обход, а не устройство мира: 30 минут одним числом склеивают актуальность
цены и жизнь брони, хотя тариф меняется раз в месяцы. Пересматриваем (задача S-22): срок
делаем длинным и настраиваемым, а протухание привязываем к событию смены версии тарифа —
тогда вместо 409 по таймеру вы получаете внятное «цена устарела, переспроси витрину», и
только когда она правда устарела. Нужна ваша оценка реального разрыва по времени (В-3).

### S-14. Идемпотентность повторного `select`

`external_ref` — ключ, а не история. Поведение (`selection.py:265-303`):

- **Тот же состав, тот же `decision_id`, тот же `coverage_scope`, срок не истёк** → ничего не
  меняется, возвращается тот же `selection_id`, тот же черновик договора, тот же номер.
  Полностью идемпотентно.
- **Другой состав** → выбор **замещается**: старые активации удаляются, создаются новые,
  `selection_id` **сохраняется тот же**, черновик договора получает новую `revision` и новую
  `document_version`, но **номер договора сохраняется** (`contract_drafts.py:76-95`). Факт в
  журнале — `additional_products.selection.replaced`. Ни 409, ни нового `selection_id`.
- **После `confirm`** → 409, замена запрещена.

То есть перевыбор состава клиентом на шаге условий — это просто повторный `select`, никаких
предварительных отмен звать не нужно. Обратите внимание: `activation_id` при замене
**меняются**, поэтому нельзя кэшировать их в реквизитах заявки раньше `confirm`.

### S-15. Отказ до select и словарь `cancel_reason`

**Отдельной операции «отказ до select» нет, и она не нужна: просто не зовите `select`.**
Решение витрины (`decision`) — это лог подбора, он и так записан, отказ клиента виден как
отсутствие selection по `external_ref`.

Если бронь уже сделана, а оформление не состоялось — есть `POST /api/v1/offerings/release`
(контракт в `answers-round-2.md`, Q-04): причина обязательна, повтор безопасен, деньги и ЕРП
не затрагиваются. Не позвали — бронь истечёт по TTL, но тогда это истечение, а не отказ.

**Словарь `cancel_reason` закрыт** по вашему В-7 и равен перечислению
`ПричиныОтменыДополнительныхПродуктов`:

| Код | Когда |
|---|---|
| `client_refused` | отказ клиента (`ОтказКлиента`) |
| `payment_missing` | отсутствие оплаты (`ОтсутствиеОплаты`) |
| `draft_expired` | проставляет сервис при истечении брони; на вход не принимается |

Всё остальное — 422. Отмена с ненулевым возвратом
требует `refund_channel` (`client_account` / `organization_account` / `loan_principal`),
иначе 422 (`cancellation.py:214`).

### S-16. Обязательный продукт

**Флага обязательности в каталоге нет.** Дерево `eligibility` отвечает только на вопрос
«показывать или нет», не «обязателен ли». Отдельного флага в схеме продукта тоже нет.

На dual-run это ровно ваш APNS-023: обязательность остаётся в `РС
ОбязательныеДополнительныеПродукты`, сервис о ней не знает и знать не должен — витрина
вернёт продукт как доступный, «обязателен» решает ТБ.

План переноса нужен, но он относится к cutover (ваш APNS-055), не к волнам 1–3, и развилка
тут не техническая:

- обязательность зависит **только от продукта** → переносим булевым флагом в каталог, дёшево;
- зависит **от условий сделки** (вид займа, канал, сумма, подразделение) → это второе дерево
  правил рядом с `eligibility`, и вести его должен владелец кредитной политики, а не владелец
  каталога. Тогда честнее оставить правило в ТБ и после cutover: сервис отдаёт доступность,
  ТБ решает обязательность.

Склоняемся к тому, что вы правы и обязательность — часть кредитной политики, а не свойство
товара. Но решение зависит от вашего ответа: В-4.

### S-17. Загрузка `ap_client_blacklist`

**API есть** (S-24, проверено на стенде): `blacklist/upsert`, `blacklist/remove`,
`blacklist/list` под правом `additional_products.blacklist.write` / `.read`, батч до 1000
записей, повтор `client_ref` внутри батча схлопывается. Право на запись есть у роли
`integration` — список ведётся у вас, синхронизировать его должен владелец данных. Примеры —
в `answers-round-2.md`.

Схема таблицы (`db_models/additional_products.py:562-575`): `source_id`, `client_ref`,
`reason`. Уникальность — композитная (`source_id`, `client_ref`): `client_ref` осмыслен только
вместе с источником.

`client_ref` — **тот же GUID контрагента 1С**, что вы шлёте в `offerings/list` и в
`parties.customer.client_ref` (S-07). Если в РС жалоб ключ другой (код ЛК, ФИО+ДР), нужна
ваша выгрузка с колонкой GUID контрагента — иначе фильтр не сойдётся. Формат первичной
заливки: CSV `client_ref;reason;created_at`, дальше дельта через API.

Фильтрация уже работает: `is_blacklisted()` (`catalog.py:441`) на каждый `offerings/list`,
результат кладётся в контекст решения как `client_is_blacklisted`, и продукт с
соответствующим правилом отсекается (`offering.py:132`). До заливки данных фильтр просто
всегда возвращает «не в списке» — то есть на dual-run ваш `CheckAdditionalProductsBlackList`
обязан остаться источником истины, наш фильтр молча ничего не отфильтрует.

### S-18. `legacy-comparison` / `loan-sample` как приёмка dual-run

> **Круг 5 (2026-08-26):** сервис **отменяет** абзац «приёмка = журнал ТБ + выгрузка S-25». Канон — `POST /api/v1/parity/observations` (обе стороны складывает сервис, роль сторон — данные). Журнал APNS-004 остаётся и шлёт наблюдения. Полный текст: [answers-round-5.md](answers-round-5.md). Ниже — исходный ответ круга 1, только как история.

**Нет, в текущем виде использовать как приёмку нельзя, и это важно понять до APNS-005.**

Оба эндпоинта — read-only отдача **статического JSON с диска**, собранного один раз вне
приложения (`api/v1/ap_analytics.py:29-48`, файлы `backend/api/data/ap_legacy_comparison.json`
и `ap_loan_sample.json`). Они не ходят в БД, не ходят в 1С, ничего не сравнивают в рантайме.

Что это на самом деле:
- `legacy-comparison` — разовый прогон «цена, которую легаси реально списала» против «цена,
  которую по тем же коэффициентам считает наша формула», по выгрузке договоров с dbprod9 за
  период. Вход — два CSV (`docs/research/ap_legacy_tariff_mapping.csv`,
  `ap_legacy_contracts_sample.csv`), сборка — `scripts/database/ap_export_legacy_comparison.py`.
  Эталон писали мы, поля сравнения: `product_code`, `tariff_code`, `requested_amount`,
  `price_charged` vs `computed_price`, статус расхождения.
- `loan-sample` — выборка сумм/сроков реальных займов для симулятора тарифов, без факта
  продажи доп-продукта.

Ни состав оффера, ни номер черновика, ни факт активации там не сравниваются.

**Что предлагаем вместо.** Приёмка dual-run — это ваш журнал интеграции (APNS-004), где на
каждую заявку лежат обе стороны: результат 1С и ответ сервиса. Матрицу полей (APNS-005)
строим от него. С нашей стороны нужен сопоставимый срез — задача S-25: эндпоинт выгрузки
решений витрины по списку `external_ref` (что показали, что отсекли и почему —
`ap_decision.rejections` это уже хранит, наружу не отдаётся). Тогда расхождение «сервис не
показал продукт X» получает причину, а не просто фиксируется.

Второй компаратор строить не надо, согласны. Но и первого пока нет — есть разовый датасет.

### S-19. Каталог и таблица соответствия

**Канон для пилота — четыре живых продукта** (на стенде сейчас доступны три: версия
`unemployment` архивирована, комбо не заведено — см. `dev-access.md`):

| `product_code` | Название | `tariff_code` |
|---|---|---|
| `guarantee` | Гарантия остановки процентов | `to_3999`, `from_4000` |
| `unemployment` | Страхование от потери работы | `to_12999`, `from_13000` |
| `sberhealth` | СберЗдоровье | `healthy_start`, `healthy_start_plus`, `path_to_health`, `path_to_health_plus`, `health_nearby`, `psychologist`, `psychologist_plus`, `psychologist_premium` |
| `cashback` | Кешбэк на лекарства | `to_13999`, `to_20999`, `from_21000` |

Плюс комбо `guarantee_health_start` (`guarantee` + `sberhealth`) — приходит в `offerings/list`
отдельным оффером с непустым полем `combo`. Учтите его в карте: комбо не раскладывается на
две отдельные продажи, оно выбирается целиком.

В вашем списке пилота (`cashback`, `guarantee`, `sberhealth`) нет `unemployment` — со стороны
каталога он готов, включать или нет, решаете вы.

**Таблица соответствия ссылкам 1С уже существует и ведём её мы**:
`docs/research/ap_legacy_tariff_mapping.csv` — 28 строк, ключ `legacy_setting_id` (код
настройки `НастройкиДополнительныхПродуктов`), значения `product_code` + `tariff_code` +
границы суммы. Она покрывает все четыре живых продукта и уже провалидирована на покрытие
(`validate_mapping_coverage`).

Что нужно от ТБ для APNS-003: подтвердить, что ключ `legacy_setting_id` — правильная точка
связи (а не GUID `Справочники.ДополнительныеПродукты` / `ПрограммыСтрахования`), и отдать
недостающие соответствия для каналов, видов операции и видов займа — их в CSV нет.

Отдельно: **`channel` не валидируется на входе**. Это `str` до 32 символов
(`offerings_requests.py:54`); неизвестный код не даст ошибки, он просто не совпадёт ни с
одним правилом eligibility, и витрина вернёт меньше офферов или ноль — **молча**. Допустимые
значения ровно четыре: `office`, `web`, `mobile_app`, `call_center`. Разведение легаси-
справочника `КаналыПродаж` на тройку (`channel`, `cash_delivery`, `platform`) у нас уже
описано и провалидировано с бизнесом — `loan_sample_export.py:25-37`, берите оттуда, это
готовый кусок карты для APNS-003. Валидация канала уже стоит (S-26): неизвестный код даёт 422
`CHANNEL_UNKNOWN` со списком известных значений в `details.known`.

### S-20. `confirm_policy` для `centrofinance`

Подтверждаем: **`explicit`** — договор подписывается вызовом `sales/confirm`, оплата приходит
отдельно и запускает услугу. Это единственный вариант для источника с займом.
`payment_triggers_activation` — режим лендинга, и при нём `sales/confirm` возвращает 409
`CONFIRM_NOT_APPLICABLE` (`sales.py:252-256`), плюс действует ограничение «одна позиция на
selection». Для ТБ он неприменим.

Значение выставляется при заведении источника (задача S-01b) и на stage, и на prod
одинаково.

## Замечания к плану реализации

План в целом принимаем: разбиение на волны, «1С остаётся source of truth», порядок
tb_api → конвейер → офис — со стороны сервиса возражений нет. Точечно:

- **APNS-010.** Маппинг входа сходится: `subdivision` и `client_is_repeat` — необязательные
  поля, они уже есть в контракте (`offerings_requests.py:61-62`). «Нал/безнал» —
  `cash_delivery`, отдельным полем от канала, не склеенным.
- **APNS-020.** См. п. 0.1: `select` зовём поздно. И не сохраняйте `activation_id` в
  реквизитах заявки до `confirm` — при перевыборе состава они меняются (S-14).
- **APNS-021.** Требует нашей доработки, см. 0.2 / S-21. До неё сценарий «бронь без
  оформления» закрывается только TTL.
- **APNS-022.** Пересчёт суммы: цена приходит **посчитанной**, коэффициенты наружу не
  отдаются вообще (закреплено тестом `test_response_never_exposes_tariff_coefficients`).
  Сравнивать надо `items[].price` и `total_price`, ничего не пересчитывая на стороне ТБ.
- **APNS-030.** `registry_data` — **не «при необходимости», а обязательно** для продуктов с
  `registry_schema != none` (`sberhealth`, `cashback`, `unemployment`). Без него `confirm`
  падает 422 «Для партнёрского реестра не хватает реквизитов продажи»
  (`registries.py:116-117`). Схемы: `sberhealth` — `agreement_number` + `client_phone`;
  `pharmiq` — ФИО + телефон; `euroins` — паспорт, ДР, номер полиса, страховая сумма
  (`sales.py:44-70`). У `guarantee` реестра нет, список пустой.
- **APNS-031.** Совпадает с нашим контрактом полностью, кроме вопроса В-1 про одно ППИ на
  несколько продуктов. `paid_at` не может быть раньше резервирования продажи
  (`payment.py:266`) — при рассинхроне часов ТБ и сервера это даёт 422, учитывайте при
  формировании `paid_at`.
- **APNS-033.** `sales/list` принимает только `external_ref` и возвращает весь selection с
  осями состояний по каждой позиции (`contract_state`, `service_state`, `money_state`,
  `partner_state`, `erp_state`, `exception_state`) — этого достаточно для сверки с
  `РС СостоянияДополнительныхПродуктов`.
- **APNS-042.** Согласны: master каталога после cutover — сервис, второго живого редактора
  тарифов быть не должно.

## Вопросы обратно в ТБ

- **В-1.** ППИ на оплату доп-продуктов — **одно на продукт или одно на заявку**? Если одно на
  несколько продуктов, текущий контракт `sales/payment` его не примет (п. 0.3): нужен либо
  составной `payment_ref` вида `<GUID ППИ>#<номер строки>` с разбивкой суммы по позициям,
  либо доработка контракта под «одна оплата — несколько активаций». Ответ определяет, есть
  ли здесь задача сервиса.
- **В-2.** Что подставлять в `coverage_scope.scope_id` в момент `select`, когда договор займа
  ещё не создан: GUID заявки или select зовётся уже после присвоения GUID договора? Решение
  должно быть одинаковым во всех точках вызова (S-08).
- **В-3.** Реальный разрыв по времени между подбором и формированием документов в офисе —
  минуты или часы? От этого зависит, какой срок жизни оффера закладывать в S-22 — и надо ли
  вам вообще держать правило «зовём select поздно» после его выкатки.
- **В-4.** Обязательность доп-продукта в `РС ОбязательныеДополнительныеПродукты` зависит
  только от продукта или ещё от условий сделки (вид займа, канал, подразделение, сумма)? От
  этого зависит, переносима ли она в правила каталога вообще (S-16 / APNS-055).
- **В-5.** Ключ в `РС ЧерныйСписокКлиентовЖалобыДополнительныеПродукты` — GUID контрагента
  или что-то иное? Если иное, нужна выгрузка с колонкой GUID (S-17).
- **В-6.** Располагает ли 1С реквизитами партнёрского реестра в точке
  `СформироватьДокументыДополнительныхПродуктов`: телефон и номер договора для
  `sberhealth`/`cashback`, паспорт, ДР, номер полиса и страховая сумма для `euroins`? Сейчас
  они обязательны на `confirm` (APNS-030), а отдельного вызова досылки реквизитов у нас нет.

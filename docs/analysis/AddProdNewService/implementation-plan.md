## Инвариант: сервис не стопает выдачу на прод-тестах

Действует во всех режимах **параллельного** вызова (`shadow`, `dual-write`) на стенде и на проде. Это правило ТБ (2026-09-03), не отдельный ответ сервиса; с кругом 5 оно стыкуется: сбой сервиса — тоже наблюдение (`timeout` / `http_error` / `not_called`), а не повод оборвать заявку.

Пока 1С source of truth:

- Недоступность, DNS, TLS, HTTP 4xx/5xx, таймаут, неразборный JSON, 401 после retry, отказ `parity/observations` **не меняют** ответ клиенту, запись реквизитов, проведение договоров/ППИ, ответ `tb_api`.
- Исключение HTTP-клиента **не всплывает** в форму, конвейер, онлайн-выдачу и HTTP-сервис. Транзакция 1С из-за сервиса **не откатывается**.
- В журнал интеграции и в лог платформы — **предупреждение**, не ошибка, из-за которой пользователь видит сбой выдачи.
- Таймаут HTTP ограничен настройкой APNS-002: для `offerings/list` канон **15–20 с** (не 5 с). Истечение = тот же fail-open, выдача без допов сервиса, без ожидания «пока сервис оживёт».
- Наблюдение всё равно пытаемся отправить (круг 5). Если и оно не ушло — 1С не откатываем; досыл по журналу позже.
- Нет распределённой транзакции с сервисом: dual-write — два независимых факта. Расхождение после сбоя сервиса — материал сверки, не инцидент выдачи.

После APNS-060 (`service-primary` на подборе) этот инвариант **снимается для того блока**, который уже считает сервис источником: сбой витрины тогда влияет на клиента. Cutover — отдельное решение, не правило прод-тестов. До 060/061/062 легаси-путь обязан быть самодостаточным.

## Инвариант: новые метаданные интеграции — только под привилегированным режимом

Точки действующих процессов (подбор доппродуктов, форма заявки, `tb_api`, конвейер) вызывают подсистему интеграции, но **не обязаны** иметь RLS/права на новые объекты волны 0–1. Иначе у оператора без роли на справочник/журнал/константы интеграция упадёт с ошибкой прав и сломает выдачу — это нарушение fail-open.

**Константы** (в т.ч. `ИспользоватьСервисДополнительныхПродуктов`, `ОсновнаяНастройкаСервисаДополнительныхПродуктов` и любые новые константы контура): привилегированный режим **не** использовать. Права чтения — только через роль `ЧтениеКонстант` (есть у всех пользователей); новые константы обязательно добавлять в `Roles/ЧтениеКонстант/Ext/Rights.xml`.

Граница привилегированного режима: внутри `ИнтеграцияСервисДополнительныхПродуктов` / `…Служебный` (и аналогов) доступ к **новым** метаданным call path, на которые у оператора выдачи нет RLS/ролей:

- справочник `НастройкиСервисаДополнительныхПродуктов` (чтение реквизитов);
- безопасное хранилище пароля / токена (уже так);
- регистр `ЖурналИнтеграцииСервисДополнительныхПродуктов` (запись/чтение);
- прочие новые объекты контура (не константы), если появятся в call path из легаси-процесса —

выполняется в `УстановитьПривилегированныйРежим(Истина)` с гарантированным сбросом (в т.ч. в `Исключение`). Вызывающий легаси-код привилегии не поднимает.

Не поднимать привилегии «на весь подбор 1С» и не маскировать ими ошибки бизнес-логики легаси. Не раздавать массово роли на справочник/журнал операторам выдачи как замену этому инварианту (роли — админам интеграции / сопровождению).

### APNS-004. Журнал интеграции и идемпотентность

Jira: [DEV-78068](https://jira.centrofinans.ru/browse/DEV-78068). **Статус: завершена** (2026-09-28). MR !6054.

Регистр/объект очереди фактов: запрос, correlation id, `decision_id`/`selection_id`/`activation_id`, HTTP-код, тело ошибки. Повтор select/confirm/payment не должен плодить вторую продажу в сервисе. Сбой записи журнала или POST наблюдения **не** прерывает выдачу; уровень — предупреждение.

**Хранение журнала (дополнение 2026-09-12):** автоматическая очистка устаревших записей журнала/наблюдений. Срок в **днях** — реквизит настроек интеграции доппродуктов (тот же объект настроек APNS-002). Цель — не раздувать ИБ JSON-телами. Регламент/метод очистки по дате записи старше N дней; 0 или пусто — поведение согласовать в коде (безопасный default или «не чистить»). Fail-open: сбой очистки не влияет на выдачу.

Плюс отправка наблюдения в `POST /api/v1/parity/observations` (право `additional_products.parity.write`, роль `integration`). Стенд с 2026-08-28 отвечает; новых учёток нет — права в роли, тот же JWT. `attempt_ref` = стабильный ключ записи журнала (ретрай той же попытки — тот же ключ; другая попытка — другой). Повтор с тем же телом → `duplicates`; с другим телом → `conflicts`, запись не меняется. Батч до 200; одна кривая строка не валит пачку. Несколько подборов по заявке — несколько наблюдений, не массив `decision_id`.

Два среза **до релиза** (круг 5, просьба 1; задним числом не восстановить):

- `available` — алгоритм в `ПрограммныйИнтерфейсДополнительныеПродукты.ПодобратьДополнительныеПродукты`;
- `shown` — то, что увидел клиент, после ручного отбора на `ЗаявкаНаВыдачуЗайма.ПодборДополнительныхПродуктов`; где отбора нет — копия `available`.

Ключи `available`/`shown` обязательны (пустой массив ок). `shown_to_client` = режим APNS-002 (`legacy` до cutover, `service` после). `decision_id` всегда в теле: **одна** непустая строка-UUID из ответа `offerings/list` при `outcome: "ok"`, иначе явный `null` (ключ есть; массив → 422 на весь батч). Наблюдение слать и при `http_error` / `timeout` / `not_called`. ПДн (ФИО, телефон, паспорт, номера договоров) не передаём. Позиции — коды `НастройкиДополнительныхПродуктов`, названия, цены, сроки; карту `product_code`/`tariff_code` ведёт сервис.

Чтение сверки — `POST /api/v1/parity/observations/export` по списку `external_ref`; склейка только по `decision_id`.

- `ЗаписатьДополнительныеПродуктыСФормы` / запись реквизитов заявки
- онлайн: `ЗаписатьДопРеквизитыДопПродуктаПоЗаявкеПриВыдачеОнлайнЗайма`

1С пишет реквизиты как сейчас. Сервис получает `external_ref` = GUID заявки, `decision_id` последнего успешного list, `offer_ids`, `coverage_scope`. Сбой `select` / отсутствие `decision_id` из-за упавшего list — предупреждение в журнале, реквизиты 1С всё равно записываются.

**Звать `select` максимально близко к формированию документов**, не на шаге подбора: TTL 30 мин, select его не продлевает. `coverage_scope.ends_at` = дата окончания договора займа, ISO-8601 с явным смещением. Повторный `list`+`select` по той же заявке штатный до confirm. `activation_id` в реквизиты заявки до confirm не класть. На select шлём два `offer_id` составляющих; сервис может свернуть в комбо (`normalized_offer_ids`).

### APNS-021. Отказ клиента и очистка выбора

Пустой `offer_ids` не используем.

- Ничего не выбрали: `offerings/select` не вызываем.
- Бронь есть, оформление не состоялось: `POST /api/v1/offerings/release` с `external_ref` и `reason` = `client_refused` | `payment_missing`. Повтор идемпотентен. После confirm release даёт 409 — тогда `/sales/cancel`.
- В 1С по-прежнему очищаются `ДополнительныеРеквизитыДополнительногоПродукта`.

Легаси-поле `activations[].state` после release может остаться `reserved`; канон — оси (`contract_state = cancelled`).

### APNS-022. Пересчет суммы на шаге условий

Цена приходит посчитанной (`items[].price`, `total_price`), коэффициенты не пересчитывать. Если `expires_at` прошёл — новый `list`+`select`, иначе confirm даст 409.

### APNS-023. Обязательные продукты и черный список

Пока сервис не считает обязательность: 1С продолжает `РС ОбязательныеДополнительныеПродукты` (измерения вид займа + канал + продукт). Чёрный список: API upsert/remove/list готов (S-24), роль `integration` пишет. До заливки РС витрина никого не отсекает. `client_ref` = GUID, только `ВСписке = true`.

**Критерий волны 2:** по пилотным заявкам в сервисе есть selection, связанный с заявкой ТБ; 1С-реквизиты не изменили поведение для пользователя. Сбой select/release на dual-write не блокирует запись/очистку реквизитов в 1С.

## Волна 3. Активация и оплата (dual-write)

### APNS-030. `sales/confirm` в точке формирования договоров

Точки 1С:

- `УправлениеДополнительнымиПродуктами.СформироватьДокументыДополнительныхПродуктов`
- конвейер / онлайн-выдача, те же вызовы после ИУ
- офис `ШагКомплектДокументов`

Передать `parties`, `loan_context`. `signed_at` лучше не слать — сервер поставит своё; «красивое» время вне окна брони → 409. `registry_data` **обязателен** для продуктов с реестром: `sberhealth` (номер + телефон), `pharmiq`/`cashback` (ФИО + телефон), `euroins`/`unemployment` (паспорт, ДР, полис, страховая сумма). У `guarantee` реестра нет.

1С по-прежнему создает и проводит `ДоговорДополнительногоПродукта*`. Сбой `sales/confirm` не отменяет проведение этих документов.

### APNS-031. Оплата при включении в тело = отдельное ППИ

Правило зафиксировано (уточнение ТБ + протокол симуляции B):

1. `payment_mode = financed`: сумма займа увеличивается (включение в тело).
2. **После этого** ТБ создает `ПлатежноеПоручениеИсходящее` на оплату доппродукта. Назначение - `payment_purpose` снимка оффера.
3. В сервис уходит `POST /api/v1/sales/payment`: `activation_id`, `payment_ref` (ключ идемпотентности факта ППИ, владелец - ТБ), `amount`, `paid_at`.

`sales/confirm` в точке оформления/выдачи **не** закрывает ось денег. После confirm штатно `money_state = pending`.

Необязательный блок `payment` внутри confirm **не реализован**. Канон: два вызова.

`payment_ref` не ИУ и не договор займа. Один `payment_ref` — одна активация, `amount` = цена позиции. `paid_at` лучше не слать (рассинхрон часов → 422); если слать — не раньше брони. ППИ одно на договор доппродукта (В-1 закрыт).

### APNS-032. `sales/payment` и webhook

Вызов из 1С в точке создания/проведения ППИ (financed) или `ОплатаЧерезПлатежнуюСистему` (upfront). Webhook Mandarin - канал лендинга, не займ в ТБ. На dual-run: **ТБ инициатор payment**. Сбой `sales/payment` не стопает проведение ППИ/ПС; факт денег в 1С уже есть, в сервис досылаем по журналу.

### APNS-033. Чтение `sales/list` только для сверки

Не подменять `GetLoanRequestAdditionalProducts`. Сверять activation_id, price, payment_state со состояниями `РС СостоянияДополнительныхПродуктов`.

**Критерий волны 3:** по пилотным выдачам `sales/payment` уходит вместе с ППИ (или ПС); `money_state = paid` не раньше ППИ и не в момент одного только включения в тело. Расхождения классифицированы. Сбой confirm/payment не откатывает договоры и ППИ в 1С.

## Волна 4. Доказательство идентичности и данные

### APNS-040. Прогон на выборке прод-подобных заявок

Использовать собственный журнал и (когда будет) выгрузку решений сервиса S-25. Admin `legacy-comparison` / `loan-sample` как приёмку dual-run не использовать.

### APNS-041. Недостающие атрибуты клиента

Если сервисный подбор пустой или беднее 1С - список полей, которых не хватает в `offerings/list` (возраст, регион, повторность, подразделение, СКД-поля). Либо расширить запрос, либо сузить пилот.

### APNS-042. Решение по master-каталогу

Владелец каталога после переключения - сервис (протокол, раздел «кто чем владеет» / «переключение с ТБ»). На dual-run не держать второй живой редактор тарифов в 1С: карта кодов + проекция, публикация версий в сервисе. Writer учетных документов ТБ в ERP выключается только вместе с включением реле сервиса (шаг 5 схемы переключения) - это не то же самое, что dual-run продаж.

## Волна 6. Cutover (отключение 1С)

Только после волн 1-4 и явно выбранного подмножества волны 5.

### APNS-060. Режим `service-primary` для подбора

`ПодобратьДополнительныеПродукты` берет состав и цены из `offerings/list`. Легаси-матчинг после этого шага **не выключается** — становится теневой стороной (`available` = легаси, `shown_to_client: "service"`). Откат флагом без выкладки. Не совмещать с APNS-063.

С этого шага инвариант fail-open **для подбора** снимается: пустой/ошибочный ответ витрины уже виден клиенту. Политика деградации (оставить пустой подбор vs аварийно показать легаси) — отдельное решение перед включением флага, не правило прод-тестов волн 1-3.

### APNS-061. Режим `service-primary` для записи выбора

Реквизиты заявки заполняются из ответа select (чтобы график 1С получил ту же сумму), либо 1С перестает хранить состав и читает `sales/list`. Второй вариант тяжелее: график и лимиты сегодня читают реквизиты. Рекомендация: **хранить проекцию в 1С**, считать в сервисе.

### APNS-062. Режим `service-primary` для факта активации/оплаты

1С продолжает проводить договоры и ППИ, но не считает это «решением о продаже»: продажа уже подтверждена сервисом. Либо наоборот - 1С проводит по факту confirm/payment. Выбрать одну оркестрацию.

### APNS-063. Выключение легаси-матчинга и легаси-записи

Отдельные флаги и **отдельный момент времени** после APNS-060 плюс период наблюдения (порог — по данным сервиса, заранее не назначаем). Одним заходом с APNS-060 нельзя: после cutover пропадёт вторая сторона сверки. Учетные документы 1С не удаляем этим шагом.

## Порядок внедрения в процессы выдачи

1. tb_api remote (`GetClientAvailableAdditionalProducts` + `EditLoanRequestAdditionalProducts`) - проще логировать и сравнивать.
2. Кредитный конвейер / онлайн-выдача - те же модули, меньше UI.
3. Офис `ШагУсловия` / `ПодборДополнительныхПродуктов` - после стабилизации API, потому что там обязательность, отказ и пересчет суммы на форме.

## Готовность к отключению 1С (чеклист)

- Карта кодов покрывает пилотную номенклатуру, пропуски не молчат.
- Shadow подбора без необъясненных расхождений цены и состава.
- Dual-write выбора и confirm/payment не расходятся по состояниям.
- `sales/payment` совпадает с ППИ (financed) или ПС (upfront), а не с фактом включения в тело.
- Есть флаг отката.
- На dual-run доказан fail-open: сбой сервиса не ломает выдачу и не откатывает учёт 1С (журнал — предупреждения + наблюдения `timeout`/`http_error`).
- Офисный и remote контуры пилота прогнаны.
- Печать, отмена, реестры - либо вынесены, либо явно оставлены в 1С решением, а не «забыты».

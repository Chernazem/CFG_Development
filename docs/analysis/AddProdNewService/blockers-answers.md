## Вопросы плана AddProdNewService

### 1. Чем ТБ авторизуется в runtime (admin-cookie дал 403)

**Ответ.** Канал 1 (ТБ и лендинг -> сервис) - JWT-принципал с привязанным `source_id`. Источник определяется по service-учетке, не по полю в теле. Админка - отдельный канал 5 (JWT + права `erp.*` / catalog admin).

403 на `POST /api/v1/offerings/list` с cookie админки **ожидаем**: это не клиент витрины. APNS-001 / S-01 = выдать ТБ JWT источника `centrofinance` (или аналог), а не расширять права admin UI.

Идемпотентность на стороне ТБ держится на `external_ref`, `payment_ref`, `cancel_ref`, `usage_ref`.

### 2. Как сказать «клиент отказался», если пустой `offer_ids` нельзя

**Ответ.** Пустой select не нужен.

- Клиент не выбрал ничего: `offerings/select` не вызывается. Черновика нет.
- Выбор забронирован, оформление не состоялось: `POST /api/v1/sales/cancel`. Ось договора: `draft` -> `cancelled`; отдельно `expired` - черновик, который так и не стал договором (не то же самое, что отмена договора).
- Номер черновика при истечении/неоформлении не возвращается в серию (дыры согласуются с бухгалтерией). «Удаляется» = пометка на удаление регламентом, след для претензий остается.

Причины отмены в легаси различают «Отказ клиента» и «Отсутствие оплаты» - в сервисе это разные `cancel_reason`, не один код.

### 3. Какой объект 1С = `payment_ref` при включении в тело

**Ответ.** Не ИУ и не договор займа.

Цепочка в ТБ и в протоколе сервиса совпадает:

1. Включение в тело: сумма займа увеличивается (`payment_mode = financed`).
2. **После этого** ТБ создает отдельное `ПлатежноеПоручениеИсходящее` на оплату доппродукта (назначение платежа берется из снимка оффера, поле `payment_purpose`).
3. Факт оплаты в сервисе - `POST /api/v1/sales/payment`. Для продажи с займом владелец факта - ТБ: `payment_ref` рождается там (в протоколе пример вида `tb-pay-...`), сумма и `paid_at` приходят снимком.

`sales/confirm` фиксирует оформление (подпись, выдача), **не** оплату. После confirm оси: `contract_state = signed`, `money_state` еще `pending`. Деньги сдвигает только payment.

Двухфазность обязательна: на проде 9,1% продаж стартуют в «Ожидает оплаты». Разрыв почти всегда меньше минуты, поэтому в контракте есть предложение передавать необязательный блок `payment` внутри confirm, когда ППИ уже есть в тот же момент. Обязательным блок делать нельзя. На dual-run безопасно: confirm в точке оформления, payment в точке создания/проведения ППИ.

Оплата вне тела / через платежную систему - тот же `/sales/payment` (или webhook канала лендинга). Для ТБ с займом webhook Mandarin не используется: прием оплаты у займа владеет ТБ.

### 4. Кто master каталога на dual-run

**Ответ.** После переключения владелец каталога (продукты, версии, тарифы, правила доступности) - **сервис**. ТБ про партнерские реквизиты не знает и знать не должен.

Порядок из раздела «Переключение с ТБ»: expand -> ТБ начинает слать `party` и `loan_context` -> сервис копит документы ERP при выключенном реле -> сверка -> дата-рубеж: релей ВКЛ и writer ТБ ВЫКЛ одновременно.

На dual-run это значит: считать и публиковать тарифы в сервисе; в 1С либо проекция/карта кодов, либо временная копия без второго редактора. Два живых редактора запрещены тем же текстом (снимок условий, а не ссылка на живой каталог).

### 5. Какой канал пилотить первым

**Ответ.** Основной путь - **продажа с займом, оформление в ТБ** (симуляция B, в образце `channel = office`, полный контекст заявки). Прямая продажа с лендинга (`standalone`, `payment_triggers_activation`) - после основного пути: там больше дыр к ERP.

Внутри ТБ по-прежнему разумно начать с tb_api/конвейера как более логируемого входа в те же методы, но бизнес-канон протокола - займ в ТБ, не лендинг.

### 6. Черный список и обязательность

**Черный список.** В сервисе есть `ap_client_blacklist` (`source_id` + `client_ref`). Витрина применяет его сама. В легаси проверку был обязан звать канал и мог не вызвать. На dual-run: ТБ передает `client_ref`; сервис фильтрует на `offerings/list`. Отдельный `CheckAdditionalProductsBlackList` для клиента ЛК можно оставить как проекцию, пока фронт его ждет, но источник истины на cutover - таблица сервиса (нужна выгрузка/синхронизация текущего РС ТБ).

**Обязательность.** В протоколе отдельного флага «обязательный продукт» на витрине нет; доступность - дерево `eligibility` версии продукта. Пока 1С не отключена, обязательность `РС ОбязательныеДополнительныеПродукты` остается проверкой ТБ. Перенос в правила каталога - отдельное решение, не следует из PDF автоматически.

## Что PDF закрыл сверх наших шести вопросов

Подтверждено протоколом и не надо выдумывать в задачах ТБ:

- Сервис не ходит в монолит: весь контекст в запросе.
- Витрина отдает **готовую цену**, не коэффициенты тарифа (в легаси API отдавал коэффициенты).
- Номер договора доппродукта выдается на `select` (черновик), печатает ТБ; кредитный договор нумерует ТБ.
- Для ТБ `confirm_policy = explicit`: ТБ зовет `/sales/confirm` при выдаче. Для лендинга confirm запрещен (409 `CONFIRM_NOT_APPLICABLE`), фиксация по оплате.
- Исполнение возврата (`refund_channel`) остается в 1С.
- GUID объектов ТБ в ERP уходят без изменений; клиент на confirm - GUID из ТБ плюс реквизиты снимка.
- Организация - атрибут сделки, приходит фактом продажи, не справочником «подразделение -> МКК».

Блокеры PDF про **релей ERP** (ключ дедупликации, формат отмены в ERP, образец «Отражение операций…», GUID поставщика) - не блокеры dual-run ТБ. Dual-run продаж может идти при выключенном реле, как шаг 3-4 схемы переключения.

Остается открытым для задач ТБ (вопрос 11 PDF / S-06): располагает ли ТБ в момент продажи ИНН, полом, ДР и полным блоком `parties.seller`. Нет поля → 422 `ERP_SNAPSHOT_INCOMPLETE`, дырявый снимок сервис не примет.

## Корректировки 2026-08-24 (код сервиса `b22bb3b`)

Источник: [answers-from-service.md](answers-from-service.md). Это «как есть сегодня», не «как должно остаться». Стенд, если расходится — передеплоить.

Перечёркивает прежние формулировки плана:

1. **TTL оффера/selection = 30 минут, `select` не продлевает.** `confirm` после `expires_at` → 409 `SELECTION_EXPIRED`. На офисной заявке `list`+`select` зовём поздно, у формирования документов. Повтор по тому же `external_ref` штатный (до confirm).
2. **`sales/cancel` не снимает неподтверждённую бронь** (`draft` → 409 `ACTIVATION_NOT_CANCELLABLE`). Бронь истекает кроном в `expired`. Явное снятие — их задача S-21 `offerings/release`. Пункт 2 выше про cancel на draft **сегодня неверен**.
3. **`payment_ref` один на активацию, сумма = цена позиции.** Одно ППИ на пачку продуктов контракт не примет. См. В-1.
4. **Токен:** login кладёт JWT в httpOnly-cookie; для 1С рабочий обход — `Authorization: Bearer` (CSRF тогда не нужен). Нормальный M2M — S-01a.
5. **Канон confirm** — вложенные `parties`, не плоский `party` из PDF. `organization` = `parties.seller`, целиком обязательно.
6. **`legacy-comparison` не приёмка dual-run** (статический JSON). Журнал ТБ + S-25.
7. Каталог пилота: четыре продукта + комбо. Карта: `legacy_setting_id` = `Code` настроек.

Открытый хвост ТБ круга 1 (В-1…В-7) закрыт в [answers-to-service.md](answers-to-service.md).

Полный текст вопросов сервиса — раздел «Вопросы обратно в ТБ» в answers-from-service.md.

## В-1. ППИ: одно на продукт или одно на заявку?

Сервис: `payment_ref` уникален на активацию, `amount` обязан совпасть с ценой позиции. Одно ППИ на несколько продуктов текущий `sales/payment` не примет.

**Из 1С.** Оплата доппродукта завязана на **договор доппродукта**, не на заявку:

- `ПлатежноеПоручениеИсходящее.ДокументОснование` = конкретный `ДоговорДополнительногоПродукта*` (запросы в `УправлениеДополнительнымиПродуктами`, разбор основания в `Документы.ПлатежноеПоручениеИсходящее`).
- Назначение платежа собирается от номера/даты этого договора.

**Черновик ответа сервису:** одно ППИ на продукт (на договор доппродукта). `payment_ref` = GUID ППИ, `amount` = цена этой активации. Составной ключ и доработка «одна оплата — несколько активаций» не нужны, если это подтвердит учет.

Нужно подтверждение владельца процесса: нет ли исключения «одно ППИ на пачку допов заявки».

## В-2. `coverage_scope.scope_id` в момент `select`, когда договора займа ещё нет

Сервис: GUID договора (глобально уникален) либо GUID заявки — но одно правило во всех точках. После confirm повторный select запрещён.

**Из 1С.** Выбор пишется в реквизиты заявки на шаге условий, договор займа появляется позже (выдача / ИУ).

**Черновик ответа:** на dual-run `select` зовём поздно (TTL 30 мин, см. 0.1 ответов сервиса) — сразу перед `СформироватьДокументыДополнительныхПродуктов`. Тогда GUID договора займа уже есть либо присваивается в той же точке. `scope_id` = GUID `Документ.ДоговорЗаймаКонтрагента` (или фактический тип договора выдачи), `kind = loan_agreement`. Не использовать номер `ЦЗ…` без префикса.

Если поздний select на каком-то контуре невозможен — запасной вариант: `scope_id` = GUID заявки во всех точках, включая confirm. Это ослабляет однократность «продукт на заём», решение надо зафиксировать явно.

## В-3. Разрыв времени подбор → формирование документов в офисе

Сервис закладывает S-22 (развести актуальность цены и жизнь брони). Пока TTL = 30 мин и `select` его не продлевает.

**Из 1С.** Офисный сценарий допускает часы между `ПодборДополнительныхПродуктов` / `ШагУсловия` и комплектом документов. Точной статистики в конфигурации нет.

**Черновик ответа:** минуты на конвейере/онлайн, **часы** в офисе — поэтому до S-22 правило ТБ: `list`+`select` максимально близко к формированию документов; ранний select на форме подбора не делать. Нужна оценка владельца офисной выдачи (медиана / p95), чтобы сервис заложил срок в S-22.

## В-4. Обязательность: только продукт или условия сделки?

**Из 1С — однозначно условия сделки.** `РС ОбязательныеДополнительныеПродукты`: измерения `ВидЗайма` + `КаналПродаж` + `ДополнительныйПродукт`, ресурс `Состояние` (`УстановитьОбязательным`). API: `ОбязательныеДополнительныеПродукты(Дата, ВидЗайма, КаналПродаж)`. Сумма и подразделение в регистре не участвуют.

**Черновик ответа сервису:** обязательность — кредитная политика, не свойство товара. На dual-run и после cutover остаётся в ТБ (APNS-023 / APNS-055). В каталог булевым флагом не переносим.

## В-5. Ключ чёрного списка жалоб

**Из 1С — GUID контрагента.** `РС ЧерныйСписокКлиентовЖалобыДополнительныеПродукты`, измерение `Контрагент` (`CatalogRef.Контрагенты`). Ресурсы: `ВСписке`, `Автор`, `Подразделение`. Кода ЛК в ключе нет.

**Черновик ответа:** `client_ref` = GUID контрагента, тот же что в `offerings/list` и `parties.customer.client_ref`. Первичная заливка: GUID + признак `ВСписке` (+ подразделение/автор в `reason` по желанию). До API S-24 источник истины dual-run — проверка ТБ.

## В-6. Реквизиты партнёрского реестра в точке формирования договоров

Сервис: на `confirm` обязателен `registry_data` для продуктов с `registry_schema != none` (`sberhealth`, `cashback`/`pharmiq`, `unemployment`/`euroins`). Отдельного вызова досылки нет.

**Из 1С.** Точка та же: `СформироватьДокументыДополнительныхПродуктов`. Документы пилота (`ДоговорДополнительногоПродуктаСберЗдоровье`, PharmIQ, страхование от потери работы) хранят свои реквизиты, но полный перечень «есть ли телефон/паспорт/полис именно в этот момент» ещё не инвентаризирован по полям confirm.

**Статус:** открыт. Нужна сверка атрибутов документов пилота со схемами `sales.py:44-70`. Если часть данных появляется позже — это задача сервиса (досылка), не обход 422 на стороне ТБ.

## В-7. Перечень причин отмены для словаря `cancel_reason`

**Из 1С.**

`Перечисление.ПричиныОтменыДополнительныхПродуктов` (две причины факта):

| Код 1С | Предлагаемый `cancel_reason` |
| --- | --- |
| `ОтказКлиента` | `client_refused` |
| `ОтсутствиеОплаты` | `payment_missing` |

`Перечисление.ВидОтменыДополнительногоПродукта` (куда возвращать деньги → `refund_channel`):

| Код 1С | `refund_channel` |
| --- | --- |
| `НаРеквизитыКонтрагента` | `client_account` |
| `НаРеквизитыОрганизации` | `organization_account` |
| `ВозвратВДоговорЗайма` | `loan_principal` |

Отказ **до** select в 1С — просто пустые реквизиты заявки, отдельного документа нет. Это совпадает с сервисом: select не звать.

До оформления (черновик) `sales/cancel` сегодня даёт 409; нужен их S-21 (`offerings/release`). Для `loan_not_issued` / `operator_error` / `cooling_period_return` отдельных значений перечисления нет — либо не слать, либо завести у нас, если процесс так маркирует.

**Черновик ответа:** отдать сервису две причины + три канала возврата. `draft_expired` проставляет сервис сам.

## Ещё на стороне ТБ, не из списка В-*

- **S-06 / confirm:** обязательны ИНН, пол, ДР физлица, полный блок `parties.seller` (юрлицо + банк + подразделение). Нет поля → 422 `ERP_SNAPSHOT_INCOMPLETE`, дырявый снимок сервис не примет.
- **APNS-003:** ключ карты у сервиса — `legacy_setting_id` (код `НастройкиДополнительныхПродуктов`), не GUID `ДополнительныеПродукты`. Подтвердить и дослать канал / вид операции / вид займа.
- **Пилот каталога:** к `cashback`, `guarantee`, `sberhealth` готов `unemployment` и комбо `guarantee_health_start`. Решить, входит ли в первую волну.
- **`contour`:** всегда `production` (можно не слать). `test` у роли `integration` нет.
- Не кэшировать `activation_id` в реквизитах заявки до `confirm` (при перевыборе они меняются, `selection_id` нет).

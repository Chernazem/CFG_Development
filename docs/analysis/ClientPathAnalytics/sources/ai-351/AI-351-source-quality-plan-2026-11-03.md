## Четыре независимые оценки

| Оценка | Что проверяет | Чего из неё не следует |
| --- | --- | --- |
| Структура | Уникальность ID, допустимые связи, покрытие когорты, инварианты мер | Все исходные данные поступили в DWH |
| Числовая проверка | Совпадение значений с эталоном для конкретного среза, мер и разрезов | Все события источника уже загружены |
| Полнота загрузки | Доказанное покрытие обязательных источников и нужной истории | Все связи однозначны и известно точное время |
| Качество связей и времени | Непривязанные документы, неоднозначности, точность событий | Записи потеряны при загрузке |

Текущая оргструктура и отсутствие произвольного исторического состояния
документа остаются ограничениями методики на существующих источниках.
Сами по себе они не устанавливают неполную загрузку.

## Правила true / false / NULL

Оценка относится к ключу: `snapshot_id`, версия профиля обязательных
источников, период когорты, момент результата и область данных/доступа.
Когорта имеет исключённую правую границу. Нельзя ограничиться загрузкой
только октября: нужны история клиентов для ID-цепочек и границ выдачи,
а также связанные результаты до `as_of_at`, включая ноябрь.
D7 и ограничение междневного разрыва не вводятся.

| Значение | Условие |
| --- | --- |
| true | Для каждого обязательного источника есть проверенное подтверждение завершённой загрузки нужной области, истории и момента результата. Подтверждение связано с данными, видимыми в срезе; необработанных обязательных частей/известных разрывов нет |
| false | Подтверждено, что обязательная часть нужной области не загружена: известный разрыв, пропущенная партиция, незавершённая обязательная партия, очередь до целевой позиции либо отклонённые обязательные записи. Причина относится именно к проверяемому периоду и scope |
| NULL | Оценки или доказательства нет, его охват/семантика не подтверждены, либо из доступной отметки нельзя установить полноту требуемой области |

Агрегация в Semantic Layer: известное false имеет приоритет; при отсутствии
false любое неизвестное обязательное подтверждение даёт NULL; true
допустимо только при покрытии всего заранее заданного профиля.
Список зависимостей нельзя строить из фактически найденных строк:
иначе отсутствующий источник исчезнет из проверки.

Пустой результат может быть полным при подтверждённой пустой загрузке.
Пустые права доступа дают отдельное `not_applicable`/`EMPTY_SCOPE`, а не
успешную оценку источников. Ошибка необязательной для профиля задачи или
партии за другим периодом не устанавливает false. Старое подтверждение,
не покрывающее целевой момент, без доказанного разрыва даёт NULL.

`MAX(event_at)`, `MAX(created_at)` и `MAX(updated_at)` описывают найденные
строки. Ни они, ни завершение D0–D1, ни успешная числовая сверка не заменяют
подтверждения загрузчика. Названия `load_max` в существующем freshness
не превращают наблюдаемую метку строки в сертификат полноты.

Для каждого источника фиксируются владелец, обязательность в версии
профиля, область/история, целевая позиция, подтверждённое покрытие,
момент оценки, код причины и ссылка на доказательство. Успешное выполнение
job без описанного охвата и гарантии фиксации данных недостаточно.
Первичная полная загрузка и обработка последующих изменений должны
покрывать необходимую историю, а не только последние партии.

### Что найдено при проверке метаданных DWH

03.11.2026 выполнено read-only исследование доступного каталога.
Подтверждённого журнала покрытия перечисленных источников не найдено.
Это ограничение проверенного подключения, не утверждение об отсутствии
журнала во всей инфраструктуре.

- `public.request_for_loan.dt` содержит время документа;
  `dt_start_loan` и `dt_end_loan` имеют тип date. Это не отметки загрузки.
- У pipeline есть `created_at`, `started_at`, `ended_at`; у `check_fail`
  временных полей нет. В текущем чтении нет доказательства окончания
  репликации обеих таблиц.
- У `tb.reg_selected_solutions` есть `created_at` и `updated_at`, но
  freshness сейчас хранит только количества. Можно добавить наблюдаемые
  максимумы с явной семантикой, не присваивая по ним true/false.
- Доступна `analytics.v_job_stats`: тип job, дата, час, длительности.
  Проверенные колонки не задают источник, покрытый период и позицию загрузки.
- У `dashaio.logs` доступны `created_at` и JSON `source`; семантика
  сертификата загрузки не подтверждена. Произвольный JSON лога не нужно
  читать или отдавать BI вместо согласованного журнала.
- Схема `monitor` недоступна по USAGE; `pgagent_maintence.mt_job_log`
  недоступна по SELECT. Требуется договорённость с владельцем DWH о
  минимальном read-only представлении подтверждений, а не расширение прав
  на все технические журналы.
- В доступных `pg_stat_subscription` и `pg_replication_slots` строк нет.
  Это не доказывает ни полноту, ни отсутствие внешнего механизма загрузки.

Рекомендуемый следующий шаг: получить от владельца DWH документированный
manifest/журнал с источником, областью и границами покрытия, целевой и
применённой позицией, состоянием обязательных частей и фиксацией результата.
Видимость подтверждения должна согласовываться с фиксацией самих данных.
До этого `source_complete` сохраняет NULL с причиной
`LOAD_EVIDENCE_UNAVAILABLE` или `HISTORY_COVERAGE_UNVERIFIED`.

## Диагностики: причины, влияние и варианты

| Диагностика | Документы / попытки | Вывод |
| --- | --- | --- |
| `orphan_intermediate` | 611 / 0 | Все документы имеют операцию «ПодтверждениеДохода», без ID договора, предшественника и кандидата попытки. У одного нет ID клиента; у всех известно собственное подразделение |
| `unknown_intraday_issue_order` | 112 / 71 связанных попытка | Один документ одновременно orphan. Из 71 попытки у 67 подтверждена выдача D0–D1, у четырёх показатель неизвестен. Флаг не превращает все 71 исход в unknown |
| `date_only_conclusion_order` | 4 / 4 | Не доказан порядок договоров внутри даты; UUID обеспечивает повторяемость, не время. В этом срезе четыре попытки имеют известное отсутствие выдачи D0–D1 |
| `date_only_first_issue_order` | 1 / 1 | У результата неизвестен порядок первых выдач; D0–D1 этой попытки остаётся NULL |

Для 609 orphan входной документ того же клиента в тот же день в сохранённой
когорте не найден. У двух такой вход есть, но между ним и промежуточным
документом найдена первая выдача с точным временем: объединение нарушило
бы границу попытки. У 110 orphan клиент имеет вход в другие дни либо другой
интервал сохранённой когорты; совпадение клиента не создаёт ID-связь.

Orphan сохранены и входят в число документов. Они не создают вход и не
попадают в distinct-знаменатель попыток без `client_attempt_id`.
Это объясняет 42 439 документов против 41 828 связанных документов;
611 нельзя прибавить к 34 860 попыткам или объявить потерянными.
Для документов с диагностикой сохраняются действующие правила всех мер.
75 затронутых попыток считаются distinct; пересечения причин не складываются.

Варианты работы с orphan:

1. Сейчас сохранять отдельную группу «Промежуточные документы без попытки»
   с собственным подразделением и исходными ссылками. Это рекомендуемый
   вариант для существующих данных.
2. Если в существующем источнике найдётся подтверждённый исходный ID,
   добавить его в нормализованное происхождение связи, проверить клиента,
   время и границу выдачи, затем пересчитать новый срез и сверить изменения.
3. При отсутствии ID оставить связь неизвестной. Поиск по клиенту за
   несколько дней, D7, ближайшая дата и отмена границы выдачи не допускаются.

Варианты уточнения времени:

- Адаптер уже использует `account_cash_warrant.dt` и
  `payment_order_outbound.dt` для совпадающего договора/дня выдачи.
  Сначала разобрать конкретные несопоставленные случаи по исходным ID,
  допустимому виду операции, проведению и удалению. Потребуется сохранить
  ссылки на события, вызвавшие неопределённость, в новой диагностике.
- `dash.data_issue.issue_dt` и `contracts_of_counterparties.dt` имеют тип
  date. `created_at`/`updated_at`, начало/конец займа и время регистрации
  статуса не подставляются как точное время выдачи или заключения.
- Для порядка заключения нужен документированный факт подписания/заключения
  с ID договора и временем события. `monitor.sign_contract` видна в каталоге,
  но недоступна; её пригодность не подтверждена. Запрос владельцу источника
  входит в план, использование таблицы пока не предлагается как готовое решение.
- Если точного события нет, сохранить точность даты, диагностику и
  применимые NULL. Сценарии проверяются на синтетических границах и
  сопоставимой реальной выборке; старые срезы не изменяются.

## Предлагаемый безопасный контракт

Глобальные `source_diagnostics`, `validation`, `freshness` остаются закрыты
при ограниченном доступе. Отдельный статус не должен возвращать их JSON,
произвольные логи, глобальные счётчики или ID чужих подразделений.

Предлагаемые поля, пока не реализованные:

| Поле | Смысл |
| --- | --- |
| `assessment_id`, `assessment_version` | Неизменяемая версия оценки конкретного среза |
| `completeness_profile_version`, `scope_basis` | Профиль обязательных источников и основание атрибуции проверяемой области |
| `load_completeness` | true / false / NULL по обязательному профилю и разрешённой области |
| `load_reason_codes` | Закрытый словарь безопасных причин, например `LOAD_EVIDENCE_UNAVAILABLE`, `COVERAGE_GAP_CONFIRMED`, `PROOF_INCONSISTENT`, `EMPTY_SCOPE` |
| `coverage_start`, `coverage_end`, `result_through_at`, `assessed_at` | Какая когорта и горизонт результата оценены, когда выполнена оценка |
| `structure_status` | passed / failed / not_assessed по протоколу структурной проверки |
| `numerical_status`, `numerical_reference_id` | passed / failed / not_assessed с областью числового протокола |
| `link_quality_status`, `quality_reason_codes` | Есть известная неопределённость / проблем не обнаружено / не оценено |
| `documents_with_quality_flags`, `attempts_with_quality_flags` | Документы и distinct-попытки разрешённого scope, с явными единицами |
| `limitations` | Постоянные ограничения профиля: текущая оргструктура, недоступность произвольного прошлого состояния |

Предпочтительная реализация: подготовить оценки и факты качества один раз
при публикации нового среза; дать Cube отдельную именованную поверхность
`client_funnel_quality` для качества попыток и статуса загрузки.
Состояния и объединённые показатели вычисляет Semantic Layer, BI выбирает
подпись и оформление. Расшифровка причин берётся из статического словаря.

Для связанных документов качество атрибутируется подразделению входа,
как основная воронка. Для orphan вход неизвестен: нужна отдельная
поверхность `client_funnel_document_quality` с
`scope_basis=source_document_division`.
У всех 611 исходных orphan собственное подразделение известно. Для них
нельзя подставлять это подразделение в атрибуцию входа попытки.
Непривязанные к разрешённому подразделению записи не раскрываются через
глобальный остаток или разность итогов.

Для обеих поверхностей обязательны дата, snapshot_id и пересечение зоны
с подписанными правами. Новые кубы должны войти в общий механизм scope
с правильным ключом атрибуции; защита не ограничивается прежними тремя
кубами. Причины, счётчики, группировки и экспорт проверяются одинаково.
Недостаток доказательства покрытия собственного scope даёт NULL;
ошибка загрузки только чужой области не должна делать свой scope false.
Отсутствие разбиения доказательства по областям не заменяется глобальными
числами. Глобальный legacy `source_complete` не используется как локальная
оценка руководителя без явно подходящего охвата доказательства.

Минимальный вариант до появления журнала: безопасные статические причины
неизвестной полноты и ограничения профиля без новых чисел. Следующий этап:
факты качества в разрешённой области. Оценка true/false включается только
после проверки контракта подтверждений DWH. Вынесенный сервисный endpoint
можно рассмотреть вместо отдельного Cube, но он потребует тех же проверок
токена, дат, scope и запрета глобальных payload; отдельный путь доступа
дублировать без необходимости не рекомендуется.

## План работ и приёмка

1. **DWH: подтверждения загрузки.** Согласовать обязательный профиль и
   минимальный журнал с владельцем; подтвердить историю, покрытие и смысл
   позиций для каждой зависимости. До получения доказательств NULL остаётся.
2. **Semantic Layer: оценка и причины.** Добавить версионированный evaluator
   и отдельные статусы. Проверить матрицу true/false/NULL, смешанные источники,
   пустую сертифицированную загрузку, отсутствие обязательной зависимости,
   старое доказательство и пустые права. История оргструктуры не меняет
   `load_completeness` сама по себе.
3. **Качество связей.** Сохранить происхождение неопределённых времён;
   разобрать 611/112/4/1 по исходным событиям, включая два разных интервала
   одного дня. Улучшать только подтверждённые ID/время, сохранять группы
   неизвестности. Проверить distinct-итоги, знаменатели и пересечения причин.
4. **Безопасный контракт.** Реализовать именованные поля и обе атрибуции,
   расширить общий scope guard. Проверить ограничения по измерениям,
   фильтрам, сортировке, выражениям, копиям metadata и экспорту. Пустые права
   не раскрывают глобальные данные; HTTP-scope не расширяет подписанный claim.
5. **Новый срез и нагрузка.** Старые строки не переписывать. Новые оценки
   связывать с новым срезом и версией профиля; отсутствие записи оценки
   у старого среза означает not_assessed/NULL. Числовой статус привязывать
   к проверенному snapshot/содержимому, методике, контракту, мерам и фильтрам.
   Повторить месячную сверку 61 показателя и профиль вкладок со статусом;
   сравнить варианты на одних данных, отдельно проверить изменившиеся
   из-за новых доказательств связи. Подтверждения и quality-факты готовятся
   при публикации; запросы BI не запускают новое чтение DWH.

BI до изменения контракта показывает true, false и NULL раздельно и
поясняет неизвестный статус. Формулы попыток и содержимое срезов остаются
в Semantic Layer. Предложенные поля не считаются опубликованными;
версия контракта пересматривается совокупно относительно выпущенной базы,
а не увеличивается за каждую промежуточную правку AI-351.

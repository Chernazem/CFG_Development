# AI-351: статусы и счётчики качества для BI

Решение заказчика от 03.11.2026: полнота для BI определяется наличием данных,
как `source_available` у других источников. Реализованы два куба в ещё
не выпущенном контракте 23.1.0. Основание оценки: `data_presence`.

| Куб | Атрибуция и состав |
| --- | --- |
| `client_funnel_quality` | Документы с попыткой, подразделение первого обращения попытки |
| `client_funnel_document_quality` | Все документы, включая orphan, по собственному подразделению документа |

Оба куба читают существующие неизменяемые таблицы `client_funnel`.
Новый расчёт DWH или изменение сохранённых строк для их подключения
не требуется. Подразделение документа не подставляется в атрибуцию входа.

## Контракт статусов

Все статусы ниже являются числовыми мерами Cube, с единицей `flag`.
BI выбирает подпись по значению, формулы остаются в Semantic Layer.

| Мера | Значения |
| --- | --- |
| `source_available` | 1: после фильтров и прав есть документы; 0: документов нет |
| `quality_ok` | 1: документы оценены, диагностик нет; 0: есть диагностика; NULL: документов нет или диагностика не сохранена |
| `structure_ok` | 1: документы есть, в опубликованном срезе сохранён успешный структурный протокол; иначе NULL |
| `numerical_check_ok` | NULL: в текущем формате среза нет числового протокола, привязанного к выбранному запросу |

Наличие диагностик не меняет `source_available` и не исключает документы
из знаменателей. При сочетании известной диагностики с неоценённым
документом `quality_ok=0`; при одних неоценённых документах остаётся NULL.
Успешный внешний отчёт не переносится автоматически на другой срез
или произвольный набор фильтров.

Для новых виджетов используется `source_available` соответствующего куба.
Поле `client_funnel_snapshot.source_complete` сохраняет прежний смысл
и сохранённые значения; в старых срезах оно остаётся NULL.
Ожидание подтверждения ETL не блокирует оценку наличия данных для BI.
Признак `data_presence` не означает гарантию поступления всех событий
из внешних систем, как и `source_available` у спящей базы.

Статусы считаются после всех отборов запроса. Шапка отчёта запрашивает их
с общими фильтрами периода и зоны; локальный фильтр причины диагностики
не должен незаметно менять смысл общей шапки.

## Счётчики и причины

| Мера | Единица |
| --- | --- |
| `documents`, `flagged_documents`, `unassessed_documents` | Distinct-документы, документы с диагностикой, документы без сохранённой оценки |
| `attempts`, `flagged_attempts` | Distinct связанных попыток |
| `intraday_order_documents`, `intraday_order_attempts` | Неизвестен порядок обращения и выдачи внутри дня |
| `conclusion_order_documents`, `conclusion_order_attempts` | Порядок заключения договоров известен только до даты |
| `first_issue_order_documents`, `first_issue_order_attempts` | Неизвестен порядок первых выдач |
| `client_funnel_document_quality.orphan_documents` | Промежуточные документы без попытки |

Группировка и фильтр `reason_code` используют закрытый словарь из
`meta.diagnostic_reason_labels`. Отсутствие диагностик имеет код `none`,
несохранённая оценка `not_assessed`. Неизвестный код превращается в
`other_link_diagnostic`; его исходный текст не возвращается.

Документ с несколькими причинами остаётся одним документом в общем итоге.
Distinct-попытки также не складываются между причинами. На поверхности
собственного подразделения одна попытка может иметь документы в разных
подразделениях, поэтому число попыток по таким строкам не складывается.
Итог зоны запрашивается отдельно. В разборе по причине специальные счётчики
относятся к этой причине, а не к другим флагам того же документа.

## Период и доступ

Обязательны один `snapshot_id equals UUID`, `attempt_day.dateRange`
и UTC. `attempt_day` остаётся московской календарной меткой когорты:
для связанных документов это начало попытки, для orphan дата документа.
Полный связанный документ может быть создан после окончания месяца
когорты. Новый куб не меняет период и правила построения самой воронки.

`client_funnel_quality` ограничивается по `entry_division_id` и
оргструктуре входа. `client_funnel_document_quality` ограничивается по
`source_division_id` и собственной оргструктуре документа, замороженной
в его `features`. Для старого формата собственный контекст входа может
использовать только сам входной документ; неизвестные родительские ключи
остаются NULL. Текущие справочники DWH во время BI-запроса не читаются.

Зона из `x-client-funnel-scope` пересекается с подписанным
`client_funnel_allowed_divisions`. Повторяющиеся и пересекающиеся узлы
не умножают строки. Пустые права дают нулевые счётчики и
`source_available=0`, остальные статусы NULL. Диагностики чужого подразделения
не меняют `quality_ok` разрешённой области.

Глобальные `validation`, `freshness`, `source_diagnostics` остаются закрыты
для ограниченного scope. Новые кубы не предоставляют эти JSON-поля,
клиентские ID или свободные тексты. Выражения и произвольные SQL-подзапросы
при ограниченном доступе отклоняются общей защитой.

Пример запроса шапки; пользовательский токен и заголовок scope передаются
тем же способом, что для основной воронки:

```json
{
  "measures": [
    "client_funnel_quality.source_available",
    "client_funnel_quality.quality_ok",
    "client_funnel_quality.structure_ok",
    "client_funnel_quality.numerical_check_ok",
    "client_funnel_quality.documents",
    "client_funnel_quality.flagged_documents",
    "client_funnel_quality.flagged_attempts"
  ],
  "filters": [{"member": "client_funnel_quality.snapshot_id", "operator": "equals", "values": ["UUID среза"]}],
  "timeDimensions": [{"dimension": "client_funnel_quality.attempt_day", "dateRange": ["2026-10-01", "2026-10-31"]}],
  "timezone": "UTC"
}
```

Для отдельной карточки непривязанных документов BI использует
`client_funnel_document_quality.orphan_documents` и соответствующий
`source_available`, явно подписывая атрибуцию по подразделению документа.
Код и bundle BI внедряются в проекте Centrofinans BI.

Месячная числовая проверка, доступ и производительность:

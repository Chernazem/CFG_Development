В скрипте найдено 21 поле с префиксом `flag_`. 
Важное уточнение: часть флагов обозначает произошедшее событие, а часть — расчётное состояние, например «ожидается выдача» или «предзаявка не завершена». Для реализации в 1С это различие нужно сохранить.

## 1. Общая воронка — 7 признаков

| Поле                       | Краткое наименование                   | Как определять, что событие произошло / условие установки `1`                                                                                                                                                 |
| -------------------------- | -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `flag_product_application` | Создана продуктовая заявка             | За день у клиента есть хотя бы одна заявка с операцией из продуктового списка SQL: `product_application_count > 0`. Операция `ПодтверждениеДохода` сюда не входит.                                            |
| `flag_contract`            | Создан договор по продуктовой заявке   | У итоговой продуктовой заявки клиента заполнен идентификатор связанного договора: `contract_id IS NOT NULL`. Если по заявке договор создан, но заявка закрыта с причиной отказа, то договор не засчитывается. |
| `flag_issue`               | Зафиксирована выдача                   | По договору итоговой продуктовой заявки найдена хотя бы одна выдача с суммой больше нуля                                                                                                                      |


Все условия этого блока соответствуют итоговому `SELECT`, а правила определения выдачи и завершения окна — блоку `application_outcomes`.

## 2. Воронка предварительной заявки — 5 признаков

| Поле                           | Краткое наименование                         | Как определять, что событие произошло / условие установки `1`                                                                                                             |
| ------------------------------ | -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `flag_preapplication`          | Создана предварительная заявка               | За день у клиента есть хотя бы одна непомеченная на удаление заявка с видом операции `Предварительная`: `preapplication_count > 0`.                                       |
| `flag_preapplication_finished` | Предварительная заявка завершена             | Есть предзаявка за день, а у выбранной для анализа предзаявки установлен успешный шаг, шаг отказа либо заполнена причина отказа.                                          |
| `flag_preapplication_success`  | Предварительная заявка завершена успешно     | Есть предзаявка за день; у выбранной предзаявки шаг входит в перечень успешных и причина отказа не заполнена.                                                             |
| `flag_preapplication_refused`  | Зафиксирован отказ по предварительной заявке | Есть предзаявка за день; у выбранной предзаявки установлен шаг отказа либо заполнена причина отказа. При наличии причины отказа отказ имеет приоритет над успешным шагом. |
|                                | Есть попытка обращения в МПР                 | Из 1С был запрос в МПР                                                                                                                                                    |


Статусы определяются по выбранной, или «якорной», предзаявке, а не по всем предзаявкам клиента за день.
### Технические значения шагов

| Назначение               | `step_id`                              |
| ------------------------ | -------------------------------------- |
| Успешный шаг — вариант 1 | `e3591cce-360b-11e7-80b9-fa9538801de8` |
| Успешный шаг — вариант 2 | `e3591ccd-360b-11e7-80b9-fa9538801de8` |
| Шаг отказа               | `5653d0ee-3c0d-11e7-80bf-a57f9d7a28fd` |

Заполненная причина отказа — `reason_for_refusal_in_loan_id IS NOT NULL`. Эти идентификаторы и правило приоритета отказа заданы в блоке `preapplications`.

## 3. Воронка МПР и выбранного решения — 9 признаков

| Поле                              | Краткое наименование                                            | Как определять, что событие произошло / условие установки `1`                                                                                                           |
| --------------------------------- | --------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `flag_mpr_started`                | Запущен МПР                                                     | Для выбранной предзаявки есть хотя бы одна неудалённая запись запуска в `tb.reg_mpr_service_ids`: `loan_request_id = preapplication_id`, `COALESCE(is_deleted, 0) = 0`. |
| `flag_mpr_no_solution`            | МПР не подобрал решений                                         | МПР запущен, но среди учитываемых SQL решений нет ни одного: группа результата `Нет решений`. Отдельного подтверждения завершения обработки МПР скрипт не проверяет.    |


Условия взяты из блоков запусков МПР, предложений, определения выбора решения, выбора лучшей попытки и итогового `SELECT`.

## 4. Общие правила, которые нужно включить в задачу разработки

### Единица учёта и выбор заявки

В текущем SQL флаги относятся к строке «клиент × календарный день». Чтобы воспроизвести их в 1С, недостаточно установить признак на произвольной заявке — необходимо сохранить правила выбора документов:

- Предзаявка: последняя предзаявка не позднее первой продуктовой заявки дня. Если подходящей нет, SQL выбирает последнюю предзаявку дня, в том числе более позднюю, чем продуктовая заявка.
- Итоговая продуктовая заявка: приоритет у заявки с выдачей, затем у заявки с договором, датированным тем же днём, затем у более поздней заявки.
- Лучшая попытка по выбранному решению: среди подходящих заявок после первого целевого действия приоритет у заявки с выдачей, затем с договором, затем у более поздней заявки.

### Правило фиксации выдачи

Для всех перечисленных флагов выдача определяется одинаково:

- источник — `dash.data_issue`;
- связь с договором — `contract_id`;
- сумма — `issue_amt > 0`;
- дата — от `contract_dt` до `contract_dt + 3` включительно.

Таким образом, `flag_issue_all` означает не «любая выдача клиента», а выдачу по договору выбранной итоговой заявки в заданном окне. Флаг не исключает транши, пролонгации, перезаключения или рефинансирование по соответствующим признакам источника.

### Какие признаки нельзя трактовать как отдельное подтверждённое событие

При постановке задачи стоит отдельно обозначить следующие ограничения текущей логики:

| Признак                                                 | Что важно не перепутать                                                                   |
| ------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| `flag_contract`                                         | Наличие связанного договора не равно подтверждённому подписанию договора.                 |
| `flag_mpr_no_solution`                                  | Отсутствие записанных решений не равно подтверждённому завершению МПР без решений.        |
| `flag_solution_selected`                                | Выбор выводится из последующего оформления, а не из отдельного события нажатия «Выбрать». |

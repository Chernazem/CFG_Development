# Предварительный список событий журнала

Дата: 2026-11-06. Черновик после разбора SQL продакта, карточки воронки и AI-351.

Цель: бизнес-аналитика текущего SQL-скрипта воронки собирается **только из таблицы лога** (плюс стабильные справочники соответствий на стороне аналитики: группы канала, семейства решений, белый список операций). Операционные документы и регистры ТБ для расчёта воронки больше не читаются.

В лог пишется факт в момент события. Не пишутся: «ожидается выдача», «окно закрылось», «предзаявка брошена», «решение выбрано», `client_attempt_id`, длина окна D0–D1/D0–D3.

## События

| № | Событие | Зачем SQL / воронке |
| --- | --- | --- |
| 1 | Предзаявка создана | `flag_preapplication`, вход попытки, разрезы канала / подразделения / новый клиент |
| 2 | Шаг предзаявки зафиксирован | finished / success / refused / abandoned по шагам |
| 3 | Причина отказа предзаявки зафиксирована | refused с приоритетом над успешным шагом |
| 4 | Запрос МПР отправлен | `flag_mpr_started`, попытки МПР по предзаявке |
| 5 | Ответ МПР получен | завершение запроса; `flag_mpr_no_solution` при нуле решений |
| 6 | Решение МПР записано | перечень предложений; product / intermediate / consulting |
| 7 | Заявка создана | продуктовая и промежуточная (`ПодтверждениеДохода` тоже); `flag_product_application`, вывод «решение выбрано» |
| 8 | Одобрение заявки зафиксировано | этап одобрения (AI-351); поздняя отмена — новое событие |
| 9 | Отказ заявки зафиксирован | отказ по продуктовой заявке |
| 10 | Договор связан с заявкой | `flag_contract` как ссылка, не заключение |
| 11 | Договор подписан клиентом | АСП или от руки; отделяет подпись от ссылки |
| 12 | Договор активирован | заключение после перевода денег (`ЗаключенДоговор`) |
| 13 | Выдача проведена | `flag_issue_*`; сумма > 0, момент, признаки транша / пролонгации / перезаключения / рефинансирования |

Итого **13 видов** событий первой итерации воронки.

## Что обязательно в каждой строке

Без этих полей SQL снова полезет в заявки и регистры.

- момент события (дата-время);
- клиент;
- вид события;
- предмет: предзаявка / заявка / договор / идентификатор запроса МПР / решение / регистратор;
- связи, известные в момент: предзаявка ↔ запрос МПР ↔ решение; заявка ↔ договор; выдача ↔ договор ↔ заявка;
- канал продаж, подразделение, организация, признак нового клиента — как были на документе;
- для заявки: вид операции, вид займа;
- для шага / отказа / одобрения: ссылка на шаг, причину, состояние;
- для ответа МПР: успех ответа, число решений;
- для решения: ссылка на подобранное решение;
- для подписи: вид АСП / от руки;
- для выдачи: сумма, признаки вида выдачи.

Свёртки «Офис / ЛК / мобильное», трайб, PRODUCT/INTERMEDIATE, «успешный шаг» по UUID — **правила аналитики** над значениями из лога, не отдельные события.

## Что SQL считает сам по логу

Не события журнала:

- якорная предзаявка / клиентская попытка / лучшая заявка;
- finished / success / refused / abandoned;
- «решение выбрано» и неоднозначность КЛ / автозайма;
- окно выдачи и «ожидается / созрело»;
- route_source, доли несвязанных заявок;
- все `flag_*` и агрегаты «клиент × день» или попытка.

## Вне первой итерации воронки

Полный Excel-скрипт ещё тянет скоринг, ПДН, налоговый статус, ПСК, возраст, пол, адрес. В 13 событий они не входят. Чтобы и эти колонки строились только из лога, позже нужны отдельные снимки признаков на ответе МПР / по предзаявке. AI-351 соцдем в контракт не берёт; для паритета с текущим SQL это отдельное решение.

## Соответствие цели

| Блок SQL | Покрывается событиями |
| --- | --- |
| Предзаявка | 1–3 |
| МПР и предложения | 4–6 |
| Продуктовая / промежуточная заявка | 7–9 |
| Договор и выдача | 10–13 |
| Расчётные флаги и окно | не пишутся, считаются из 1–13 |

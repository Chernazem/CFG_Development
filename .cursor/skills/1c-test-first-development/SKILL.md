# Test-first: доработка основной конфигурации или расширения (1С + YaxUnit)

## Когда применять

Пользователь просит **доработать функциональность** в **основной конфигурации** (`src/cf` / выгрузка конфигурации) или в **расширении основной конфигурации**. Тесты обычно живут в **отдельном расширении тестирования** (YaxUnit + проектные модули), реже — в другом согласованном месте.

В workspace **TB** на машине `TB-PC` проверка кода и прогон YAXUnit идут через **EDT MCP** (`docs/setup/edt-mcp.md`): `get_project_errors` вместо LSP, `run_yaxunit_tests` вместо vrunner/`1cv8c`. Команды vrunner ниже — запасной контур.

## Принцип: test-first (красный → зелёный)

Порядок **обязателен**, пока пользователь явно не отменил TDD.

1. **Понять поведение**: критерии приёмки, граничные случаи, контекст сервер/клиент.
2. **Написать тест** на это поведение (один сценарий или минимальный набор) в расширении тестирования.
3. **Проверить код через LSP диагностику, затем собрать и загрузить расширения** в тестовую ИБ. Перед сборкой код расширения YaxUnit и дорабатываемого расширения всегда должен прогоняться через LSP диагностику для исключения синтаксических ошибок. Для корректного «красного» прогона необходимо загрузить **и тестовое расширение (YaxUnit)**, **и тестируемое расширение (продукт)** в его текущем (до доработок) состоянии. Это нужно, чтобы тест мог обратиться к методам продукта и упасть по логике (assertion), а не из-за синтаксической ошибки отсутствия метода. Запустить тесты и зафиксировать результат:
   - **Ожидаемо «красный»**: падение по утверждению, ошибка выполнения, отсутствие нужного API — то есть тест **действительно проверяет** новую функциональность.
   - Если тест **сразу зелёный** — тест слишком слабый, проверяет не то или функциональность уже есть; **усилить тест** или уточнить у пользователя требование **до** написания продукта.
4. **Реализовать** функциональность в **продукте** (основная конфигурация **или** расширение — в зависимости от задачи).
5. **Загрузить продукт** в ту же тестовую ИБ (см. переменные и команды ниже).
6. **Снова запустить тот же тест** (тот же фильтр/набор). **Ожидаемо «зелёный»**.
7. При регрессии — цикл из раздела «Падения после зелёного».

Кратко: **тест → красный → код → загрузка в ИБ → тот же тест → зелёный**.

## Запрещено

- Внедрять функциональность **до** первого «красного» прогона согласованного теста (кроме явного отказа пользователя от test-first).
- Подставлять фиксированные пути, версии платформы, имена задач **без согласования**.
- Считать `Пропустить` / `skipped` полноценной заменой **падающего** сценария для TDD: для test-first нужна явная **ошибка** или **failure** по ожиданиям, иначе цикл «красный» не доказан.
- Собирать статический контекст теста конструкторами в BSL (`СоздатьЭлемент`, `СоздатьДокумент`, запись регистра). Данные — в XML-макетах фикстур, см. `repos/conf-main/src/AGENTS.md` → «Фикстуры».

## Переменные (запросить у пользователя, если не заданы)

| Переменная | Назначение |
|------------|------------|
| `PRODUCT_KIND` | Что меняется: `cf` — основная конфигурация; `extension` — расширение основной. |
| `CF_SRC` | Каталог выгрузки **основной** конфигурации (нужен при `PRODUCT_KIND=cf` или для сверки `#Удаление` в расширении). |
| `EXTENSION_SRC` | Каталог выгрузки **расширения** (при `PRODUCT_KIND=extension`). Должен быть абсолютным путем. |
| `EXTENSION_NAME` | Имя расширения в ИБ и второй аргумент `vrunner compileext` (из `Configuration.xml` расширения). |
| `TEST_EXT_SRC` | Исходники расширения тестирования (YaxUnit + тесты). Должен быть абсолютным путем. |
| `TEST_EXT_NAME` | Имя расширения тестирования в ИБ для `compileext`. |
| `TEST_IB_CONN` | Подключение к тестовой ИБ для vrunner: `/F...` или `/S...` в кавычках. |
| `V8_VERSION` | Версия платформы для `--v8version`. |
| `RUNNER` | Команда `vrunner` (или аналог). |
| `PLATFORM_BIN` | Каталог с `1cv8c` для запуска тестов. |
| `YAXUNIT_RUN_CONFIG` | Путь к JSON с `RunUnitTests=...` или эквивалент. |
| `LOCALE_UTF8` | При кириллице в путях: `export LC_ALL=ru_RU.UTF-8 LANG=ru_RU.UTF-8` (или `C.UTF-8`). |

Опционально: `PROJECT_ROOT`, `JUNIT_REPORT`, **команда обновления ИБ из основной конфигурации** — если в проекте не `compileext`, а `vrunner compile` / `updatedb` / другой сценарий: спросить у пользователя **точную команду** или шаблон из CI (`LOAD_CF_TO_TEST_IB` как осмысленное имя переменной).

### Определение пути к 1cv8c нужной версии

**Не подставлять шаблонные пути**. Путь к `1cv8c` определяется **фактическим расположением нужной версии платформы** в системе:

```bash
find /opt -path "*<версия>*1cv8c" 2>/dev/null
find /Applications -path "*<версия>*1cv8c" 2>/dev/null
find /Users -path "*<версия>*1cv8c" 2>/dev/null
```

После определения сохранить каталог в переменную `PLATFORM_BIN` и проверить:
```bash
"$PLATFORM_BIN/1cv8c" --version
```

### Загрузка продукта в тестовую ИБ

- **`PRODUCT_KIND=extension`:**

```bash
$LOCALE_PREFIX $RUNNER compileext "$EXTENSION_SRC" "$EXTENSION_NAME" \
  --updatedb --ibconnection "$TEST_IB_CONN" --ibcmd --v8version "$V8_VERSION"
```

- **`PRODUCT_KIND=cf`:** выполнить **принятую в репозитории** команду загрузки выгрузки `CF_SRC` в `TEST_IB_CONN` (не хардкодить; взять у пользователя или из `README`/скриптов CI).

### Альтернативный способ загрузки расширений (через EPF)

В некоторых проектах расширения загружаются **не через `compileext --updatedb`**, а через сборку в `.cfe` и загрузку через EPF `ЗагрузитьРасширениеВРежимеПредприятия`.
Для этапа тестирования (даже для "красного" прогона) необходимо собрать и загрузить **оба** расширения (тестовое и продуктовое):

```bash
# 1. Сборка расширений в .cfe (используйте абсолютные пути для --src)
vrunner compileexttocfe --src "$TEST_EXT_SRC" --out ".temp/$TEST_EXT_NAME.cfe" --ibcmd --v8version "$V8_VERSION"
vrunner compileexttocfe --src "$EXTENSION_SRC" --out ".temp/$EXTENSION_NAME.cfe" --ibcmd --v8version "$V8_VERSION"

# 2. Загрузка тестового расширения
vrunner run --ibconnection "$TEST_IB_CONN" --v8version "$V8_VERSION" \
  --command "Путь=$(pwd)/.temp/$TEST_EXT_NAME.cfe;Имя=$TEST_EXT_NAME;Перезаписывать;ЗавершитьРаботуСистемы;ОтключитьЛогикуНачалаРаботыСистемы" \
  --execute '$runnerRoot/epf/ЗагрузитьРасширениеВРежимеПредприятия.epf'

# 3. Загрузка продуктового расширения
vrunner run --ibconnection "$TEST_IB_CONN" --v8version "$V8_VERSION" \
  --command "Путь=$(pwd)/.temp/$EXTENSION_NAME.cfe;Имя=$EXTENSION_NAME;Перезаписывать;ЗавершитьРаботуСистемы;ОтключитьЛогикуНачалаРаботыСистемы" \
  --execute '$runnerRoot/epf/ЗагрузитьРасширениеВРежимеПредприятия.epf'
```

Использовать, если в проекте принят такой способ загрузки расширений.

### Загрузка расширения тестирования и запуск

```bash
$LOCALE_PREFIX $RUNNER compileext "$TEST_EXT_SRC" "$TEST_EXT_NAME" \
  --updatedb --ibconnection "$TEST_IB_CONN" --ibcmd --v8version "$V8_VERSION"
```

```bash
"$PLATFORM_BIN/1cv8c" ENTERPRISE \
  /IBConnectionString "File=\"<путь_к_файловой_базе_из_TEST_IB_CONN>\";" \
  /DisableStartupMessages /DisableStartupDialogs \
  /C "RunUnitTests=$YAXUNIT_RUN_CONFIG;ОтключитьЛогикуНачалаРаботыСистемы"
```

Строку `File=...` согласовать с `TEST_IB_CONN` (экранирование под ОС).

**Важно:** имя run-конфига, логов, отчётов и exitcode-файлов **привязывать к тестируемому расширению** (например `DEV_74416`), а не к `YAXUNIT`.

Пример структуры run-конфига:
```json
{
  "showReport": false,
  "closeAfterTests": true,
  "logging": {
    "level": "INFO",
    "console": true,
    "file": "/path/to/artifacts/<TEST_PREFIX>_test.log"
  },
  "reportFormat": "junit",
  "reportPath": "/path/to/artifacts/<TEST_PREFIX>_report.xml",
  "exitCode": "/path/to/artifacts/<TEST_PREFIX>_exitcode.txt",
  "filter": {
    "tests": [
      "<ИмяТестовогоМодуля>",
      "<ИмяТестовогоМодуля>.<ИмяТестовогоМетода>"
    ]
  }
}
```

## Падения после зелёного или в цикле TDD

- **Тест неверно описывает требование** → правка теста → снова **compileext** тестового расширения → прогон (при сомнении снова проверить «красный» на коммите без фикса продукта).
- **Ошибка в продукте** → правка в `CF_SRC` или `EXTENSION_SRC` → загрузка продукта в ИБ → при необходимости **compileext** тестового расширения → прогон.
- Не смешивать правку теста и продукта в одном шаге без явной причины.

## Технические замечания

- **Проверка кода**: Код расширения `yaxunit` и дорабатываемого расширения (продукта) **всегда** проверять перед сборкой/накатом. На TB-PC — EDT MCP `get_project_errors` по изменённым объектам. Если EDT MCP недоступен — `lsp-skill diagnostics` / `ReadLints`.
- **Абсолютные пути**: Всегда используйте полные (абсолютные) пути для параметра `--src` во всех командах `vrunner` (например, `--src "/Users/k1rpi/Documents/repo/TB/src/cf"`).
- **Версия платформы**: Обязательно добавляйте параметр `--v8version $V8_VERSION` во **все** команды `vrunner` (`update-dev`, `compileexttocfe`, `run` и т.д.).
- **Расположение тестов**: Тесты для расширений обычно добавляются в виде новых общих модулей (например, `ОМ_Тесты_ПрограммныйИнтерфейсЗаявкаНаВыдачуЗайма`) внутри расширения `yaxunit` (или аналогичного тестового расширения).
- `compileext` всегда с **двумя** позиционными аргументами: каталог, **имя** расширения.
- `&ИзменениеИКонтроль`: блоки `#Удаление` должны совпадать с актуальным текстом базового модуля в `CF_SRC`.
- Настройки YaxUnit: по возможности отключить интерактив сохранения отчёта (`showReport`, `closeAfterTests`).
- **Не использовать `vrunner xunit` как универсальную команду запуска YAXUnit**, если в проекте фактический запуск делается через `1cv8c ENTERPRISE ... /C "RunUnitTests=<json>;ОтключитьЛогикуНачалаРаботыСистемы"`.
- В некоторых проектах требуется суффикс `;ОтключитьЛогикуНачалаРаботыСистемы` внутри параметра `/C` при запуске тестов.

## Чеклист для агента

- [ ] Уточнены `PRODUCT_KIND`, пути и имена расширений.
- [ ] Измененный код (тесты и продукт) проверен через EDT MCP (или LSP, если MCP недоступен) перед сборкой.
- [ ] Тест написан и зарегистрирован; первый прогон **красный** (или ослабление/уточнение теста задокументировано).
- [ ] Реализация внесена **после** красного этапа.
- [ ] Продукт загружен в тестовую ИБ; тестовое расширение собрано при изменении тестов.
- [ ] Повторный прогон **того же** теста — зелёный; отчёт проверен при ненулевом коде выхода.
